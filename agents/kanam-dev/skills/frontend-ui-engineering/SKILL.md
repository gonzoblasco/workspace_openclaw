# Frontend UI Engineering

## Overview

Build production-quality user interfaces that are accessible, performant, and visually polished. This skill integrates **accessibility standards (WCAG 2.1 AA)**, **design system adherence**, and **component generation prompts** to create UIs that look like they were built by a design-aware engineer - not generated by AI.

## When to Use

- Building new UI components or pages
- Modifying existing user-facing interfaces
- Implementing responsive layouts
- Adding interactivity or state management
- Fixing visual, accessibility, or UX issues
- Creating reusable component patterns from design specs

## 🧭 Design Thinking Before Code

Esta seccion asume que ya existe una direccion estetica. Para UI nueva sin direccion definida, ver la skill `design-direction`.

Antes de escribir código de UI, el diseño se piensa en artefactos planos. Es el mismo
contrato de intención de `openspec-pattern` ("el qué antes del cómo"), aplicado al eje
visual. Aplica a **UI nueva**; para cambios menores alcanza con anotar el cambio sobre
el wireframe existente.

### Wireframe ASCII como primer artefacto

Para toda UI nueva, el primer entregable es un boceto ASCII del layout: estructura de
bloques, jerarquía visual y ubicación del CTA. **No se escribe código de layout sin
wireframe.** El boceto vive junto al proposal/contract de `openspec-pattern`, así el
diseño queda versionado antes de implementarse.

```
┌────────────────────────────────────┐
│ Header: logo · nav                 │
├────────────────────────────────────┤
│ Hero: H1 + subtítulo               │
│ [ CTA primario ]                   │
├─────────────────┬──────────────────┤
│ Card destacada  │ Card secundaria  │
├─────────────────┴──────────────────┤
│ Footer (texto muted)               │
└────────────────────────────────────┘
```

El wireframe define jerarquía (qué domina la vista), flujo de lectura y ubicación del
CTA. Color y movimiento no van acá; se deciden en las fases 2 y 3.

### Micro-sintaxis de animación

Notación compacta para *planificar* el movimiento antes de codearlo. Cada línea declara
la intención; se traduce a CSS/transiciones recién en la fase de código:

- `hover: 200ms [Y0->-2, shadow^]`
- `fadeIn: 400ms ease-out [Y+20->0, a0->1]`

Duraciones canónicas (elegir de esta tabla, no inventar por caso):

| Momento | Duración  | Easing   |
|---------|-----------|----------|
| Entry   | 300-500ms | ease-out |
| Hover   | 150-200ms | -        |
| Press   | 100-150ms | -        |

**Regla dura:** todo motion respeta `prefers-reduced-motion` - con la preferencia
activa, el movimiento se degrada (fade u opacidad inmediata), nunca se ignora. La
micro-sintaxis es planificación; no reemplaza la verificación, que cierra el loop con
`a11y-at-validation`.

### El orden: layout → tema → animación → código

El diseño se piensa en cuatro fases, en este orden:

1. **Layout** - wireframe ASCII: estructura, jerarquía, CTA.
2. **Tema** - solo tokens semánticos propios (`--primary`, `--muted`, `--border`):
   color, tipografía y espaciado salen del sistema. Iconografía con **Lucide**; nunca
   emojis como iconos.
3. **Animación** - micro-sintaxis: solo el movimiento que comunica, con
   `prefers-reduced-motion` previsto desde el plan.
4. **Código** - recién acá se implementa, con el pipeline del resto de esta skill
   (CSS Modules, tokens, verificación).

El orden encuadra con `incremental-implementation` (slices verticales, eje de diseño):
cada fase es verificable antes de la siguiente, y el layout se corrige antes de
invertir en animación.

## 📐 Reglas de calidad visual

Reglas cortas y verificables sobre el resultado final: cada una aterriza en CSS/código
concreto (tokens, selectores, medidas) y no se queda en concepto. Complementan la
micro-sintaxis de la sección "Design Thinking Before Code" y el checklist de
verificación de esta skill; no las duplican.

### Neutros siempre con tinte

Los neutros llevan una pizca de tinte (warm gray o cool gray); nunca gris puro:

```css
/* ✗ gris puro: es el tell #1 de UI generada */
--muted: #888;              /* hsl(0 0% 53%), mismo problema */

/* ✓ pizca de tinte */
--muted: hsl(30 3% 55%);    /* warm gray */
--muted: hsl(220 4% 55%);   /* cool gray */
```

Un neutro con tinte se lee intencional y no cuesta legibilidad.

### Dark mode: base con tinte, nunca negro puro

Fondo oscuro `#0f0f0f` (o su equivalente oklch), nunca `#000000`: el negro puro aplasta
y no deja profundidad ni jerarquía por elevación. Las capas suben desde esa base:

```css
--bg: #0f0f0f;         /* oklch(0.17 0 0) */
--surface-1: #16161b;  /* elevación: sube y conserva el tinte del tema */
```

### Easing y duraciones canónicas

Curva base para las transiciones: `cubic-bezier(0.16, 1, 0.3, 1)` (fast-in, slow-out).

```css
--ease-out-expo: cubic-bezier(0.16, 1, 0.3, 1);
--dur-micro: 150ms;    /* micro-interacciones: rango 100-200ms */
--dur-view: 400ms;     /* transición de página o vista: rango 300-500ms */
```

**Reglas duras:** micro-interacciones entre 100ms y 200ms; transiciones de página entre
300ms y 500ms; nada por encima de 600ms. Prohibido bounce y elastic easing. Los rangos
son los de la tabla de duraciones de la micro-sintaxis; esta sección aporta la curva
canónica, el techo de 600ms y la prohibición de bounce/elastic. La regla dura de
`prefers-reduced-motion` sigue vigente tal cual.

### Medidas de lectura

```css
.prose { max-width: 65ch; }        /* bloque de texto corrido */
.page-shell { max-width: 1280px; margin-inline: auto; } /* contenedor amplio */
```

El texto de lectura se corta en `65ch`; el contenedor amplio queda en `1280px`.

### Elegir fuente por contexto

La elección de tipografía sigue la regla de `design-direction` y depende del contexto;
nunca es una prohibición absoluta de una familia:

- **Herramienta funcional** (dashboard, form, tabla): Inter o system-ui son una decisión
  válida por legibilidad, densidad y carga instantánea.
- **Pieza memorable** (landing, portfolio, marca): fuente con carácter.

Los catálogos de fuentes en tendencia son ejemplos, no criterio: se elige por contexto.

## 🧱 Patrones CSS de produccion

Patrones de CSS en producción para el stack de esta skill (CSS Modules sobre tokens
semánticos): layout con Grid y Flexbox, tipografía y spacing fluidos, profundidad y
motion. Complementan "Reglas de calidad visual" y la fase responsive; los tokens, la
curva base de motion y la regla de dark mode siguen mandando ahí, así que esta sección
solo agrega lo que esa base no cubre. Las reglas de a11y de acá se citan por criterio
WCAG con su número (última subsección).

### Grid vs Flexbox: tabla de decisión por contexto

| Contexto             | Herramienta                        | Por qué |
|----------------------|------------------------------------|---------|
| Estructura de página | Grid con `grid-template-areas`     | Regiones nombradas: el layout completo se lee y se reordena sin tocar el markup |
| Barra de navegación  | Flexbox                            | Eje único: los ítems fluyen y se alinean en una sola dirección |
| Card grid            | Grid `auto-fill` / `auto-fit`      | Responsive sin media queries (ver `clamp()` más abajo) |
| Centrado             | `place-items: center`              | Una línea, sin trucos de transform ni márgenes negativos |
| Sidebar + contenido  | `grid-template-columns: 250px 1fr` | El `1fr` ocupa el resto, sin `calc` |
| Superposición        | Grid stacking (`grid-area: 1/1`)   | En vez de `position: absolute`: ver siguiente subsección |

Criterio general: dos dimensiones que se coordinan (filas y columnas que se ajustan
entre sí) -> Grid; un solo eje de distribución -> Flexbox.

### Superposición con Grid stacking

Para superponer elementos (badge sobre imagen, overlay sobre card, fondo debajo del
texto), compartir la celda en vez de sacar el elemento del flujo:

```css
.layered { display: grid; }
.layered > * { grid-area: 1 / 1; } /* todas las capas comparten la celda (1,1) */
```

Por qué: es más predecible que `position: absolute`, el elemento sigue en el flujo (la
celda mide su contenido más grande, no hay que fijar alturas a mano) y evita los
stacking contexts que `absolute` con `z-index` suele crear. `position: absolute` queda
para elementos que realmente flotan fuera del layout del componente.

### Tipografía y spacing fluidos con `clamp()`

`clamp(min, preferido, max)` acota el valor entre un mínimo y un máximo con una
preferencia que escala con el viewport: reemplaza saltos de breakpoint por curvas
continuas.

```css
font-size: clamp(2rem, 1.5rem + 2.5vw, 3.5rem);
padding-block: clamp(2rem, 1rem + 4vw, 6rem);
grid-template-columns: repeat(auto-fit, minmax(min(100%, 20rem), 1fr));
```

El `min(100%, 20rem)` dentro de `minmax()` evita el overflow cuando la columna mínima
no entra en un contenedor angosto. La escala tipográfica del sistema sigue definiendo
qué valores existen; `clamp()` los vuelve fluidos entre breakpoints.

### Container queries: el componente responde a su contenedor

```css
.card-area { container-type: inline-size; }

.card-title { font-size: 1rem; }

@container (min-width: 28rem) {
  .card-title { font-size: 1.25rem; }
}
```

La query se dispara por el ancho del contenedor, no del viewport: la misma card queda
bien en un sidebar angosto y en el main. Complementa la estrategia mobile-first de la
fase responsive: layout de página por breakpoint, adaptación fina por componente con
`@container`.

### Surface layering: profundidad por luminosidad, no por sombras

La profundidad se construye con luminosidad en capas, no invirtiendo colores ni
apilando drop shadows:

```css
--surface-0: hsl(220 15% 8%);   /* page */
--surface-1: hsl(220 15% 12%);  /* card */
--surface-2: hsl(220 15% 16%);  /* raised */
--surface-3: hsl(220 15% 20%);  /* modal */
```

Cada nivel sube la luminosidad y conserva el tinte: la versión tokenizada de la regla
de dark mode de "Reglas de calidad visual" (base con tinte, nunca negro puro, capas que
suben desde la base). La sombra queda como refuerzo puntual cuando el sistema lo pide;
la escala de surfaces es el sistema de profundidad.

### Motion por propósito: apertura y cierre asimétricos

Los tokens canónicos (`--ease-out-expo`, `--dur-micro`, `--dur-view`) y los rangos
duros de "Reglas de calidad visual" siguen mandando. Esta tabla agrega los momentos
que faltaban, con duración y carácter de easing por interacción:

| Momento          | Duración | Easing      | Por qué                                  |
|------------------|----------|-------------|------------------------------------------|
| Hover puntual    | 150ms    | ease-out    | rango micro                              |
| Modal open       | 250ms    | ease-out    | la capa entra desacelerando              |
| Modal close      | 200ms    | ease-in     | asimétrico: sale más rápido, acelerando  |
| Page transition  | 300ms    | ease-in-out | límite inferior del rango de vista       |
| Micro-feedback   | 100ms    | ease-out    | límite inferior del rango micro          |

El carácter ease-out lo resuelve la curva base `--ease-out-expo`; el cierre de modal es
la única desviación consciente: sale con `ease-in` y en menos tiempo (`200ms`), porque
lo que desaparece no necesita presentación. Todo queda bajo el techo de `600ms` y la
prohibición de bounce/elastic.

**Stagger reveal:** las listas y grids que entran, entran escalonadas con
`animation-delay` de 50-80ms por ítem. Con la preferencia `prefers-reduced-motion`
activa, el stagger desaparece (regla dura vigente: fade simple o nada).

### `gap` en el contenedor, no margin en los hijos

```css
.list { display: grid; gap: 1rem; }  /* ✓: el contenedor distribuye */
.list > * + * { margin-top: 1rem; }  /* ✗: margin-collapse y overrides responsive */
```

Razón: `gap` elimina de raíz los bugs de margin-collapse (sin excepciones
`:first-child` / `:last-child`) y simplifica el responsive: al cambiar de breakpoint se
ajusta un solo valor del contenedor. Los márgenes de un bloque respecto de sus
secciones vecinas siguen siendo del bloque.

### Tokens en tres capas: primitive -> semantic -> component

```css
/* capa 1: primitive - valores crudos de la escala, sin propósito */
--cool-300: hsl(220 15% 75%);
--cool-500: hsl(220 15% 55%);
--cool-700: hsl(220 15% 35%);

/* capa 2: semantic - propósito. Acá viven --primary, --muted, --border.
   (valores ilustrativos: el punto es la estructura de capas) */
--primary: var(--cool-700);
--muted: var(--cool-500);
--border: var(--cool-300);

/* capa 3: component - alias con alcance de un componente */
--button-primary-bg: var(--primary);
```

Los componentes leen capa 3 (o 2), nunca un primitive directo. Cambiar de tema es
remapear la capa 2: los mismos `--primary`, `--muted`, `--border` pasan a apuntar a
otros primitives y la UI completa cambia sin tocar un componente.

### Criterios WCAG citados por número

Cuando esta skill o un handoff documente una regla de a11y, citar el criterio con su
número, no solo el tema: **2.4.7** focus visible, **2.5.8** target size (WCAG 2.2),
**2.3.3** animation from interactions. El número es verificable contra la spec y mapea
a las reglas de axe-core: formaliza con criterio numerado lo que el checklist de la
fase de accesibilidad ya hace.

## 🧹 Inline Styles → CSS Modules

One `.module.css` per component, semantic classes, values unchanged. Dynamic styles → conditional classes (`selected`, `:disabled`, `[aria-pressed='true']`). Class maps typed `string | undefined` (CSS module imports are `string | undefined` under `noUncheckedIndexedAccess`).

## 🎨 Phase 1: Design System Integration

### File Structure (Colocated Components)

```
src/components/
  TaskList/
    TaskList.tsx           # Component implementation
    TaskList.test.tsx      # Tests + accessibility checks
    TaskList.stories.tsx   # Storybook stories
    use-task-list.ts       # Custom hook (complex state)
    types.ts               # Component-specific types
    _story-prompt.md       # AI generation prompt for component
```

### Design Tokens Integration

When creating components, ensure alignment with:
- **Color palette**: Use semantic tokens (`text-primary`, `bg-surface`) not raw hex values
- **Typography hierarchy**: Follow the design system's type scale
- **Spacing scale**: Use consistent increments (0.25rem or equivalent)
- **Border radius**: Consistent values from design tokens
- **Motion**: Respect motion preferences and transition durations

## ♿ Phase 2: Accessibility (WCAG 2.1 AA Compliance)

Every component must meet these accessibility standards:

### ✅ Keyboard Navigation Checklist
```tsx
// Every interactive element must be keyboard accessible
<button onClick={handleClick}>✓ Accessible</button>
<div onClick={handleClick}>✗ Not focusable - FIX REQUIRED</div>
<div role="button" tabIndex={0}>✓ But prefer <button></button></div>
```

### ✅ ARIA Labels Implementation
- Label interactive elements that lack visible text: `<button aria-label="Close dialog">`
- Label form inputs with proper associations: `<label htmlFor="email">Email</label><input id="email">`
- Use `aria-label` when no visible label exists

### ✅ Focus Management Strategy
```tsx
// Move focus when content changes
function Dialog({ isOpen, onClose }) {
  const closeRef = useRef(null);
  
  useEffect(() => {
    if (isOpen) closeRef.current?.focus(); // Trap focus inside dialog
  }, [isOpen]);
  
  return <dialog open={isOpen} aria-labelledby="dialog-title">...</dialog>;
}
```

### ✅ Screen Reader Testing Workflow
1. Use screen reader (VoiceOver, NVDA, JAWS) to navigate the component
2. Check that navigation order is logical and meaningful
3. Verify that skip links work and announce content properly
4. Ensure error states are announced with clear messages
5. Test focus management on dynamic content updates

### ✅ Empty & Error States (No Blank Screens)
```tsx
// ✗ BAD - blank screen
if (tasks.length === 0) return null;

// ✓ GOOD - meaningful empty state
if (tasks.length === 0) {
  return (
    <div role="status" aria-label="No tasks">
      <EmptyStateIcon className="mx-auto h-12 w-12 text-muted"/>
      <h3>No tasks yet</h3>
      <p>Get started by creating your first task</p>
      <Button onClick={onCreateTask}>Create Task</Button>
    </div>
  );
}
```

## 📱 Phase 3: Responsive Design (Mobile-First)

### Breakpoint Strategy
Test at these critical breakpoints:
- **320px** - Minimum mobile width
- **768px** - Tablet portrait
- **1024px** - Tablet landscape
- **1440px** - Desktop entry point
- **1920px+** - Large desktop monitors

### Mobile-First Implementation
```tsx
// Tailwind: mobile-first responsive
<div className="
  grid grid-cols-1       /* Mobile: single column */
  sm:grid-cols-2         /* Small: 2 columns */
  md:grid-cols-3         /* Medium: 3 columns */
  lg:grid-cols-4         /* Large: 4 columns */
  gap-4
">
```

## ⚡ Phase 4: Loading & Transitions

### Skeleton Loading (Not Spinners)
```tsx
function TaskListSkeleton() {
  return (
    <div className="space-y-3" aria-busy="true" aria-label="Loading tasks">
      {Array.from({ length: 3 }).map((_, i) => (
        <div key={i} className="h-12 bg-muted animate-pulse rounded"/>
      ))}
    </div>
  );
}
```

### Optimistic Updates
Use optimistic UI updates with proper fallbacks when implementing mutations.

## 🔒 Phase 5: Component Architecture Patterns

### Composition over Configuration
```tsx
// ✓ GOOD - Composable
<Card>
  <CardHeader>Title</CardHeader>
  <CardBody>Content</CardBody>
</Card>

// ✗ BAD - Over-configured (prop drilling nightmare)
<Card title="Title" variant="large" bodyPadding="md">...</Card>
```

### State Management Hierarchy
```
Local state (useState)          → Component-specific UI state
Lifted state                    → Shared between 2-3 sibling components
Context                         → Theme, auth, locale (read-heavy, write-rare)
URL state (searchParams)        → Filters, pagination, shareable UI state
Server state (React Query, SWR) → Remote data with caching
Global store (Zustand, Redux)   → Complex client state app-wide
```

### Avoid Prop Drilling > 3 Levels
If you're passing props through components that don't use them, introduce context or restructure the component tree.

## 🚫 Common Anti-Patterns to Avoid

| Anti-Pattern | Why It's Bad | Production Fix |
|--------------|--------------|----------------|
| Excessive gradients | Add visual noise, clash with design systems | Flat colors matching design tokens |
| Rounded everything (rounded-2xl) | Ignores corner radius hierarchy in real designs | Consistent border-radius from design system |
| Purple/indigo everywhere | Makes every app look identical to AI-generated apps | Use project's actual color palette |
| Generic hero sections | Template-driven, no connection to actual content | Content-first layouts from real copy |
| Lorem ipsum placeholder text | Hides layout problems that real content reveals | Realistic placeholder content (approximate lengths) |
| Oversized padding everywhere | Destroys visual hierarchy and wastes space | Consistent spacing scale |
| Stock card grids | Layout shortcut that ignores information priority | Purpose-driven layouts |
| Shadow-heavy design | Layered shadows slow rendering on low-end devices | Subtle or no shadows unless design system specifies |

## 🔍 Verification Checklist

After building UI, verify all of the following:

- [ ] Component renders without console errors
- [ ] All interactive elements are keyboard accessible (Tab through the page)
- [ ] Screen reader can convey the page's content and structure
- [ ] Responsive: works at 320px, 768px, 1024px, 1440px, 1920px+
- [ ] Loading, error, and empty states all handled
- [ ] Follows the project's design system (spacing, colors, typography)
- [ ] No accessibility warnings in dev tools or axe-core
- [ ] No inline styles or arbitrary pixel values
- [ ] Focus management works correctly on dynamic content
- [ ] Color is not the sole indicator of state (use icons/text/patterns too)

## Common Rationalizations & Reality Check

| Rationalization | Reality |
|-----------------|---------|
| "Accessibility is a nice-to-have" | It's a legal requirement in many jurisdictions and an engineering quality standard. |
| "We'll make it responsive later" | Retrofitting responsive design is 3x harder than building it from the start. |
| "The design isn't final, so I'll skip styling" | Use the design system defaults. Unstyled UI creates a broken first impression for reviewers. |
| "This is just a prototype" | Prototypes become production code. Build the foundation right. |
| "The AI aesthetic is fine for now" | It signals low quality and will need rework later. Use the project's actual design system from the start. |
| "I'll add ARIA labels after the feature works" | Accessibility comes first. Implement semantic HTML and ARIA from day one. |

## Verificacion

- [ ] El componente responde a teclado completo: tab, enter, escape, flechas donde aplique.
- [ ] El foco es visible y no se pierde al re-renderizar.
- [ ] Los contrastes estan medidos contra la superficie real, no contra el token declarado.
- [ ] La UI funciona con `prefers-reduced-motion` y sin animaciones.
- [ ] Hay una captura o test que prueba el estado vacio, el de error y el de carga.

## Red Flags (Immediate Action Required)

- Components with more than 200 lines → Split them
- Inline styles or arbitrary pixel values → Extract to CSS variables or design tokens
- Missing error states, loading states, or empty states → Add all three
- No keyboard navigation testing → Test immediately
- Color as the sole indicator of state → Add icons/text/patterns
- Generic "AI look" (purple gradients, oversized cards, stock layouts) → Refactor to match design system

## AI Generation Prompts for Components

When using AI to generate components, use these prompts:

```markdown
Generate a React component that is:
1. Accessible by default (keyboard navigable, ARIA labels where needed)
2. Responsive by default (mobile-first approach)
3. Semantic HTML (use proper tags: button not div for clicks)
4. Using design tokens from the project (spacing, colors, typography)
5. No inline styles (CSS modules or styled-components)
6. Testing included (unit + E2E)

Avoid:
- Arbitrary pixel values
- Gradient backgrounds unless specified
- Color-only state indicators
- Prop drilling beyond 3 levels
```
