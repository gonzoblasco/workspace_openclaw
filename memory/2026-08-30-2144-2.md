### B) Flujo del Evento

1.  **Disparo:** Una acción en la DB (ej. `insert` en `orders`) dispara un **Webhook de Supabase** hacia una Edge Function "Dispatcher".
2.  **Enrutamiento:** El Dispatcher identifica el `tenant_id` y el `user_id`, y publica el evento en la **Cola de Mensajes** con un `eventId` único para deduplicación.
3.  **Procesamiento:** Un Worker consume el mensaje y consulta las **Preferencias**:
    *   ¿El Tenant permite notificaciones de este tipo?
    *   ¿El Usuario ha optado por recibirlo vía Push, Email o In-App?
4.  **Despacho:** El Worker envía la carga útil a los proveedores correspondientes (FCM para Push, Resend para Email).
5.  **Entrega In-App:** Se inserta el registro en la tabla de notificaciones; **Supabase Realtime** empuja el cambio al frontend de React instantáneamente.
6.  **Cierre:** Se registra el estado final en la tabla de **Auditoría**.

### C) Esquema de Tablas (SQL)

```sql
-- 1. Configuración global por Tenant
CREATE TABLE tenant_notification_settings (
    tenant_id UUID PRIMARY KEY REFERENCES tenants(id),
    enabled_channels TEXT[], -- ['push', 'email', 'in_app']
    updated_at TIMESTAMPTZ DEFAULT now()
);

-- 2. Preferencias granulares por Usuario
CREATE TABLE user_notification_preferences (
    user_id UUID PRIMARY KEY REFERENCES auth.users(id),
    tenant_id UUID REFERENCES tenants(id),
    channel_preferences JSONB, -- { "billing": ["email"], "alerts": ["push", "in_app"] }
    updated_at TIMESTAMPTZ DEFAULT now()
);

-- 3. Almacén de notificaciones In-App (y deduplicación)
CREATE TABLE notifications (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    event_id TEXT UNIQUE, -- Id externo para deduplicación
    user_id UUID REFERENCES auth.users(id),
    content JSONB,
    is_read BOOLEAN DEFAULT false,
    created_at TIMESTAMPTZ DEFAULT now()
);

-- 4. Auditoría de entregas
CREATE TABLE notification_audit_log (
    id BIGSERIAL PRIMARY KEY,
    notification_id UUID REFERENCES notifications(id),
    channel TEXT, -- 'email', 'push', 'in_app'
    status TEXT, -- 'sent', 'delivered', 'failed'
    error_message TEXT,
    delivered_at TIMESTAMPTZ DEFAULT now()
);
```

### D) Riesgos de Diseño y Mitigación

1.  **Riesgo:** Tormenta de notificaciones (Thundering Herd) durante eventos masivos del sistema.
    *   **Mitigación:** Implementar *Rate Limiting* y *Debouncing* en el Dispatcher y usar colas con prioridad para evitar que alertas críticas queden atrapadas tras notificaciones marketing.
2.  **Riesgo:** Duplicidad de mensajes debido a la entrega *at-least-once* de la cola.
    *   **Mitigación:** Implementar un patrón de *Idempotencia* en el Worker utilizando la restricción `UNIQUE` sobre `event_id` en la tabla de notificaciones.
3.  **Riesgo:** Latencia elevada en el envío de emails afectando el hilo del Worker.
    *   **Mitigación:** Desacoplar el envío de email en una cola secundaria específica para proveedores externos, evitando que un timeout de API bloquee el flujo de notificaciones in-app.

### E) Trade-off de Diseño

**Decisión:** Utilizar **Supabase Realtime (Postgres Changes)** para las notificaciones in-app en lugar de implementar un servidor de WebSockets propio (ej. Socket.io).

**Por qué:** En un entorno SaaS multi-tenant, gestionar el estado de conexiones, el escalado de sockets y el aislamiento de canales manualmente introduce una complejidad operativa masiva. Aunque pierdo un control granular sobre el protocolo de transporte, gano una integración nativa con la base de datos y una reducción drástica en el tiempo de desarrollo y mantenimiento, delegando la infraestructura de tiempo real a la plataforma.
