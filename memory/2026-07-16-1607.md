## El estado actual

CSN hoy es **Next.js 15** como base. Eso significa:
- **Frontend:** React 19 + App Router (pages, layouts, server components)
- **Backend:** API Routes (Next.js maneja el server)
- **Un solo deploy:** Vercel (o donde sea, pero Next.js necesita un server)

## Lo que proponés

Separar frontend y backend:
- **Frontend:** React 19 puro (Vite, sin Next.js)
- **Backend:** Node.js (Express, Hono, o lo que sea)

## Pros y contras

### ✅ Pros de separar

**1. Menos complejidad cognitiva**
Next.js es un framework que hace muchas cosas. Cuando tenés React + Node separados, cada uno hace lo suyo y la frontera es clara. No tenés que pensar "esto es server component o client component?", "esto va en route handler o en una API aparte?".

**2. Backend independiente**
Si querés agregar WebSockets, workers, colas, o cualquier cosa que no sea HTTP request-response, en Next.js es forzado. En Node.js aparte, es natural. Podés tener un server de WebSockets al lado del HTTP sin drama.

**3. Deploy flexible**
Next.js te ata a un runtime que entienda Node.js (Vercel, Railway, tu propio server). Con React + Vite, el frontend es estático — lo servís desde cualquier CDN (Cloudflare Pages, Netlify, S3 + CloudFront). El backend va donde quieras.

**4. Menos vendor lock-in**
Si mañana querés cambiar de framework frontend (aunque no creo), es más fácil si no está todo mezclado con el server.

**5. Tiempo de build y dev**
Vite es más rápido que Next.js en dev. El HMR de Vite es instantáneo. Next.js mejoró pero sigue siendo más pesado.

### ❌ Contras de separar

**1. Dos deploys, dos dominios, CORS**
Ahora tenés que manejar CORS, dos URLs, dos procesos. Es un overhead operativo chico pero real. Con Next.js es un solo deploy y las API routes están en el mismo origen.

**2. Server Components**
Perdés Server Components de React. Si bien podés usar React Router o TanStack Router del lado del cliente, no tenés el modelo de streaming, suspense en server, etc. Para muchos proyectos no importa, pero es una pérdida técnica.

**3. Estado compartido frontend-backend**
En Next.js, podés tener tipos compartidos entre frontend y backend porque están en el mismo proyecto. Separados, necesitás un paquete compartido o generar tipos desde el backend.

**4. El template API de CSN pierde sentido**
Hoy CSN tiene `--template api` que es Next.js sin frontend. Si separamos, ese template sería directamente un proyecto Node.js aparte, no un "template de CSN".

**5. Más decisiones**
Next.js te da un opinionated path. React + Vite + Node te da más libertad pero también más decisiones: qué router frontend (React Router, TanStack Router), qué backend (Express, Hono, Fastify), cómo compartir tipos, etc.

## Mi opinión

**No lo haría como reemplazo de CSN.** CSN es un scaffold de Next.js y está bien que lo sea. Next.js es el estándar de facto para apps React fullstack, y cambiarlo sería redefinir el producto.

**Pero sí lo haría como un template adicional.** `--template node` o `--template fullstack` que genere:
- Frontend: Vite + React 19 + React Router o TanStack Router
- Backend: Hono o Express + Drizzle + SQLite
- Un paquete compartido para tipos
- Docker Compose para correr todo local
- Y que el frontend sepa hablarle al backend

Eso te da lo mejor de ambos mundos:
- CSN sigue siendo el scaffold Next.js opinado
- Pero también tenés una opción para proyectos donde querés separar frontend y backend
- Y podés migrar proyectos de a uno: algunos en Next.js, otros en Node.js aparte
