Es decir: deepseek-v4-flash:cloud (modelo de razonamiento) se quedo MINUTOS en su 'Thinking...' interno sin emitir ningun token, y stream_model era un generador SIN timeout -> la UI quedaba esperando frames vacios para siempre (parecia colgado; el server no lo estaba). Fix aplicado en 2 capas: (1) REASONING_BUDGET subido de 2048 a 8192 (ya estaba, del fix anterior - para prompts que si terminan y emiten largo); (2) TIMEOUT de primer token en stream_model: STREAM_EMPTY_TIMEOUT_S=90s - si el modelo no emite NINGUN token en ese plazo, corta el stream y el ultimo yield lleva un aviso ('El modelo no emitio respuesta en Ns...'), en vez de dejar la UI generando vacios para siempre. Verificado con test real (umbral bajado a 3s para test): el prompt de razonamiento corto a los 3.0s y devolvio el aviso. Tambien corregi el docstring de stream_model (dije '(generador, ok)' pero el codigo devuelve un generador de strings - alineado). Aclaracion importante para Gonzo: NO era necesario relanzar el server (estaba OK), y el fix no 'desbloquea' ese prompt en particular - si el modelo tarda mas de 90s en emitir su primer token, va a salir el aviso de timeout; la causa de fondo es que deepseek-v4-flash:cloud con ese tipo de razonamiento extremo puede tardar mucho/tirar vacio.
