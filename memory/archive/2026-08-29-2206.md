## 1. Modelo de ejecución

### Decisión: Multi-agente (orquestador + workers), con un solo LLM "caro" por tarea

**Topología:**

```
GitHub Issue
    │
    ▼
[Orquestador]  ← LLM, contexto mínimo, decide el plan
    │
    ├── [Worker: Análisis]     ← LLM, lee archivos bajo demanda
    ├── [Worker: Implementación] ← LLM, escribe código
    ├── [Worker: Verificación]  ← DETERMINISTA (no LLM)
    └── [Worker: PR]           ← DETERMINISTA (templates)
```

### Trade-offs concretos

| Dimensión | Single-agent (tool loop) | Multi-agente (elegido) |
|---|---|---|
| **Latencia** | Menor (1 round-trip de contexto) | Mayor (handoffs entre workers) |
| **Costo de tokens** | **Mucho mayor** - cada tool call re-envía el contexto acumulado | Menor - cada worker recibe solo su slice |
| **Drift de contexto** | **Alto** - el contexto crece sin límite, se contamina | Bajo - cada worker arranca limpio con un brief |
| **Coordinación** | Ninguna (simple) | Compleja - requiere protocolo de handoff |
| **Fallo de un agente** | Falla todo, hay que re-ejecutar desde cero | El orquestador puede re-lanzar solo el worker que falló |
| **Resultado incorrecto** | Difícil de aislar dónde se corrompió | Se puede auditar por etapa |

**Justificación de la elección:** en un monorepo de 200k+ líneas, el problema dominante es el **drift de contexto**. Un single-agent que acumula 50 tool calls de lectura de archivos va a terminar con un contexto de 100k+ tokens donde el modelo pierde el hilo. El costo de tokens de re-enviar ese contexto en cada llamada es el killer. El multi-agente paga el costo de coordinación (que es determinista y barato) para ganar en aislamiento de contexto y en recuperación granular.

**Qué pasa cuando un agente falla:**
- **Worker de análisis muere** → el orquestador re-lanza solo ese worker con el mismo brief. No se repite nada.
- **Worker de implementación produce código incorrecto** → la verificación determinista lo atrapa ANTES de que llegue al PR. El orquestador re-lanza con el error de verificación como feedback.
- **El orquestador muere** → es el único punto de falla. Se mitiga con persistencia de estado (sección 5): el plan ya está guardado, se retoma desde donde quedó.

**Qué haría distinto con presupuesto 10x menor:** volvería a single-agent con tool loop, pero con un **contexto estrictamente limitado** (máx 20k tokens) y un planificador determinista que pre-selecciona archivos. Sacrificaría aislamiento por simplicidad y costo.

**Con presupuesto 10x mayor:** agregaría un **worker de revisión de pares** (un segundo LLM que revisa el diff del worker de implementación antes de verificar). Esto atrapa bugs lógicos que los tests no ven. Hoy ese costo no se justifica.

## 2. Gestión de contexto

### Decisión: Índice estático + lectura bajo demanda + planificador determinista

**El problema:** 200k líneas no caben en contexto. La clave es que **el agente no necesita entender el monorepo, necesita encontrar los archivos relevantes a un issue**.

### Qué se indexa (una vez, fuera de línea)

1. **Mapa de paquetes** (`packages/*/package.json`): nombre, exports públicos, dependencias, scripts. Esto es un JSON pequeño y estable.
2. **Índice de símbolos** (via `tsc --declaration` o un indexer como `ast-grep`): para cada símbolo exportado, en qué archivo vive. Esto permite resolver "el issue menciona `Button`" → "está en `packages/ui/src/Button.tsx`".
3. **Mapa de contratos públicos**: los exports de cada paquete, que son el "API surface" que no se debe romper (crítico para la sección 3).
4. **Historial de issues resueltos**: mapeo issue → archivos tocados, para que issues similares encuentren rápido los archivos relevantes.

### Qué se lee bajo demanda

- **Solo los archivos que el planificador determinista selecciona** como relevantes al issue.
- El worker de implementación recibe: el issue, el plan, y los archivos relevantes (contenido completo, no snippets, para que no alucine sobre el contexto).

### Cómo se decide qué archivos son relevantes

**Planificador determinista (no LLM):**
1. Extraer tokens del issue (nombres de símbolos, nombres de paquetes, términos).
2. Matchear contra el índice de símbolos → archivos candidatos.
3. Matchear contra el historial de issues similares → archivos tocados antes.
4. Resolver dependencias: si el issue toca `Button`, incluir los archivos que importan `Button` (via el grafo de imports del índice).
5. **El LLM del orquestador refina** este candidato inicial, pero la base es determinista. Esto evita que el LLM "decida" arbitrariamente qué leer.

### Cómo se evita la contaminación del contexto

- **Contexto efímero por worker:** cada worker arranca con un brief limpio. No hereda el contexto de los otros.
- **TTL en el índice:** el índice se regenera en cada push a `main`. Si un archivo cambió después de que el worker lo leyó, la verificación lo detecta (el diff no aplica limpio) y se re-lee.
- **No se cachea contenido de archivos entre issues.** Cada issue arranca fresco. El único cache persistente es el índice de símbolos (que es estructural, no de contenido).

**Qué haría distinto con 10x menos tokens:** indexaría solo el mapa de paquetes y el API surface (sin índice de símbolos completo). El planificador usaría matching por nombre de paquete + grep simple. Menos precisión, mucho menos costo de indexación.

**Con 10x más:** indexaría también los tests (para que el worker de implementación vea los tests existentes del archivo que toca) y el historial de diffs (para que el worker entienda patrones de cambio previos en ese archivo).

## 3. Verificación y confianza

### Decisión: Pipeline de verificación en capas, con una "puerta de seguridad" determinista

```
Worker de implementación
    │
    ▼
[1. Typecheck]  tsc --noEmit  →  errores de tipos
    │
    ▼
[2. Lint]       biome/eslint  →  estilo + reglas
    │
    ▼
[3. Tests]      vitest run     →  tests del paquete tocado + dependientes
    │
    ▼
[4. Build]      tsc build / tsup  →  compila el paquete
    │
    ▼
[5. Contrato público]  ← DETERMINISTA, la puerta clave
    │
    ▼
[6. Diff review]  LLM de bajo costo revisa el diff contra el issue
    │
    ▼
[7. PR]
```

### La puerta de seguridad: verificación de contrato público

Este es el punto que más cuidado requiere. El agente puede "alucinar" una API que no existe, o romper un export público.

**Cómo se detecta:**
- **Antes del cambio:** snapshot del API surface de cada paquete (los exports públicos, generado por `tsc --declaration` + un script que extrae los nombres exportados).
- **Después del cambio:** regenerar el snapshot y **diffearlo contra el anterior**.
- **Regla:** si un export público cambió de firma o desapareció, el PR se marca como **"breaking change"** y requiere aprobación humana explícita, sin importar que los tests pasen. Los tests del paquete no atrapan esto porque los consumidores externos no están en el monorepo.

**Falsos positivos:**
- Un cambio que agrega un export nuevo NO es breaking (solo se marca como "nuevo API").
- Un cambio de firma que es aditivo (agrega un parámetro opcional) se marca como "potencialmente breaking" y se revisa manualmente.
- **Regla de oro:** ante la duda, marcar como breaking y pedir revisión. El costo de un falso positivo es una revisión humana de 2 minutos; el costo de un falso negativo es romper el build de un consumidor externo.

**Cómo se decide si un cambio es "seguro" para mergear sin revisión humana completa:**
- **Merge automático** solo si: todos los checks pasan, el contrato público NO cambió, el diff es pequeño (< 200 líneas), y el issue es de tipo "fix" (bug claro, no feature).
- **Revisión humana** si: cambia el contrato público, el diff es grande, o el issue es ambiguo (feature request, refactor).

**Qué haría distinto con 10x menos tokens:** eliminaría el paso 6 (diff review con LLM). La verificación determinista (pasos 1-5) es suficiente para la mayoría de los fixes. El diff review es un lujo de calidad.

**Con 10x más:** agregaría **tests de mutación** (mutar el código y ver si los tests lo atrapan) para medir la calidad real de la cobertura, y un **worker de revisión de pares** que revisa el diff con ojo crítico antes de mergear.

## 4. Seguridad y límites

### Decisión: Modelo de permisos por categoría de acción + auditoría inmutable + kill switch

### Matriz de permisos

| Acción | Nivel | Aprobación |
|---|---|---|
| Leer archivos, correr tests/lint/build | **Seguro** | Automática |
| Crear rama, commit, push | **Seguro** | Automática |
| Abrir PR | **Seguro** | Automática |
| Modificar código de un paquete | **Seguro** | Automática |
| **Modificar CI** (`.github/workflows/*`) | **Peligroso** | **Humana explícita** |
| **Borrar ramas** | **Peligroso** | **Humana explícita** |
| **Publicar release a npm** | **Crítico** | **Humana explícita** |
| **Cambiar contrato público** | **Crítico** | **Humana explícita** |
| **Acceder a secretos** (npm token, GH token) | **Nunca** | Prohibido |

**Principio clave:** el agente **nunca tiene acceso directo a los secretos**. Los secretos viven en el CI runner (GitHub Actions), no en el entorno del agente. El agente solo puede disparar workflows que usan los secretos, y esos workflows tienen su propio gate de aprobación humana.

### Cómo se previene la exfiltración de secretos

1. **Los secretos no están en el entorno del agente.** Punto. No hay forma de que los lea.
2. **Red de confianza:** el agente solo puede hacer `git push` a ramas de feature, nunca a `main` directamente. Todo pasa por PR.
3. **Scrub de logs:** cualquier output de comando que contenga un patrón de secreto (token, key) se redacta antes de guardarse en el log.
4. **No hay `curl` a destinos arbitrarios.** El agente solo puede hacer llamadas a la API de GitHub (vía el SDK autenticado), no a URLs arbitrarias. Esto evita el vector clásico de "el agente hace POST de los secretos a un servidor del atacante".

### Cómo se audita cada acción

- **Log inmutable por acción:** cada acción del agente (comando ejecutado, archivo tocado, API llamada) se registra en un log append-only (no se puede editar). Incluye: timestamp, worker, comando, hash del estado antes/después.
- **El log es un artefacto del PR:** cada PR generado incluye el log completo de acciones que lo produjeron. Un humano puede auditar qué hizo el agente.

### Cómo se maneja un agente en loop infinito o que hace daño

- **Budget de pasos:** cada worker tiene un máximo de N pasos (ej: 30). Al superarlo, se aborta y se reporta "no convergió".
- **Budget de tokens:** cada worker tiene un tope de tokens. Al superarlo, se aborta.
- **Kill switch global:** un flag que detiene todos los workers en curso. Se activa manualmente o automáticamente si se detecta un patrón de daño (ej: más de X archivos borrados, push a `main`, intento de acceso a secretos).
- **Rate limiting:** el agente respeta los rate limits de GitHub/npm. Si se acerca al límite, pausa en vez de forzar.
- **Rollback:** como todo pasa por PR, revertir es tan simple como cerrar el PR o revertir el merge. Nunca se toca `main` directamente.

**Qué haría distinto con 10x menos tokens:** simplificaría la auditoría (log plano en vez de append-only inmutable) y el scrub de logs (regex simple en vez de detección heurística). La matriz de permisos se mantiene igual - no es negociable.

**Con 10x más:** agregaría **detección de intención maliciosa** (un LLM que revisa los diffs en busca de código que exfiltra datos, inyecta backdoors, o modifica la lógica de auth) antes de mergear. Hoy el costo no se justifica para un repo de confianza, pero para un repo público con contribuidores externos sería valioso.

## 5. Recuperación de fallos

### Decisión: Máquina de estados persistida en el repo + idempotencia por issue

### Qué se guarda

Un directorio `.agent-state/` en el repo (o en un store separado si no se quiere contaminar el repo):

```
.agent-state/
  issues/
    <issue-id>/
      state.json        # máquina de estados
      plan.md           # el plan aprobado
      briefs/           # briefs de cada worker
      artifacts/        # diffs intermedios, logs de verificación
```

**`state.json`** contiene la máquina de estados:

```json
{
  "issueId": "1234",
  "status": "implementing",   // analyzing | planning | implementing | verifying | pr_open | done | failed
  "currentWorker": "implement",
  "attempts": 2,
  "branch": "fix/1234-button",
  "prNumber": null,
  "checksPassed": { "typecheck": true, "lint": true, "tests": null, "build": null, "contract": null },
  "createdAt": "...",
  "updatedAt": "..."
}
```

### Cómo se retoma una tarea interrumpida

- **Cada worker es idempotente:** recibe un brief + un estado, y produce un resultado. Si muere, el orquestador lo re-lanza con el mismo brief. El worker no tiene memoria de "lo que ya hice" - el estado lo tiene el orquestador.
- **El orquestador lee `state.json` al arrancar** y continúa desde el último estado completado, no desde cero.
- **Los diffs intermedios se guardan** en `artifacts/`. Si el worker de implementación murió a mitad, el orquestador puede retomar desde el último diff válido en vez de re-generar todo.

### Cómo se evita duplicar trabajo (dos PRs para el mismo issue)

- **Idempotencia por issue:** antes de arrancar, el orquestador verifica si ya existe un PR para ese issue (via la API de GitHub, buscando PRs que referencien el issue). Si existe, no crea otro - retoma el existente o reporta.
- **La rama es determinista:** `fix/<issue-id>/<slug>`. Si el worker muere y se relanza, usa la misma rama. No crea ramas nuevas.
- **Lock por issue:** un registro en el store indica qué issue está siendo procesado. Si otro orquestador intenta procesar el mismo issue, se rechaza.

**Qué haría distinto con 10x menos tokens:** guardaría solo `state.json` (sin briefs ni artifacts intermedios). El retome sería menos granular (re-ejecutar el worker completo en vez de retomar desde un diff intermedio), pero el estado básico se mantiene.

**Con 10x más:** guardaría **snapshots del contexto** de cada worker (el brief + los archivos leídos) para que un retome no tenga que re-leer los archivos. Esto reduce latencia de retome, a costa de más almacenamiento.

## 6. Métricas y observabilidad

### Decisión: Métricas de resultado + métricas de proceso, con un "score de salud" compuesto

### Métricas de resultado (lo que importa)

| Métrica | Qué mide | Cómo se usa |
|---|---|---|
| **Tasa de PRs mergeados** | % de PRs del agente que se mergean (vs. se cierran o abandonan) | La métrica principal de calidad. < 50% = el agente produce basura. |
| **Tiempo por issue** | Desde que llega el issue hasta que se mergea el PR | Latencia. Si crece, el agente está atascado. |
| **Costo por issue** | Tokens consumidos + tiempo de cómputo por issue | Eficiencia. Si crece sin mejorar la tasa de merge, hay drift. |
| **Tasa de errores** | % de issues donde el agente falla (no converge, verificación falla, crash) | Salud del sistema. |
| **Tasa de revisión humana** | % de PRs que requirieron intervención humana | Balance autonomía/control. Muy alta = el agente no ahorra trabajo. |

### Métricas de proceso (para diagnosticar)

- **Distribución de pasos por worker:** cuántos pasos tarda cada worker. Si el worker de implementación tarda 25 pasos en promedio, el brief está mal redactado.
- **Tasa de re-lanzamiento:** cuántas veces se re-lanza un worker por crash. Alta = problema de estabilidad.
- **Tasa de falsos positivos de verificación:** cuántos cambios marcados como "breaking" en realidad no lo eran. Alta = el detector de contrato es demasiado conservador.

### Cómo se decide si el agente mejora o empeora

- **Score de salud compuesto:** `merge_rate × 0.4 + (1 - error_rate) × 0.3 + (1 - review_rate) × 0.3`. Se calcula por ventana de 30 días.
- **Regresión:** si el score baja más de 10% en dos ventanas consecutivas, se investiga. Las causas típicas: el índice de símbolos está desactualizado, un paquete cambió de estructura, el modelo subyacente cambió.
- **A/B de prompts:** cuando se cambia el prompt del orquestador o de un worker, se corre en un subconjunto de issues (10%) y se compara el score contra el baseline. Solo se promueve el cambio si mejora el score.

**Qué haría distinto con 10x menos tokens:** mediría solo las métricas de resultado (merge rate, tiempo, costo). Las métricas de proceso son diagnósticas, no operativas - se pueden sacrificar.

**Con 10x más:** agregaría **tracing distribuido** (cada paso del agente emite un span con contexto) y **análisis de regresión de calidad** (correlacionar cambios en el modelo/prompt con cambios en la tasa de merge, controlando por tipo de issue).

## 7. Trade-off final

### Sacrificaría: velocidad

**Decisión explícita:** si tuviera que sacrificar una dimensión, sacrificaría **velocidad** para ganar en **calidad** (y por extensión, seguridad).

**Por qué velocidad y no otra:**

- **No sacrifico seguridad** - es la dimensión no negociable. Un agente que filtra secretos o rompe un contrato público de un paquete publicado a npm causa daño irreparable a consumidores externos. El costo de un incidente de seguridad es órdenes de magnitud mayor que el costo de un issue que tarda 10 minutos más.
- **No sacrifico costo** - el costo de tokens es el que escala con el uso. Si el agente es caro por issue, se usa menos, y el sistema entero pierde valor. La velocidad es más elástica: un issue que tarda 2 horas en vez de 30 minutos es aceptable si el resultado es correcto.
- **No sacrifico calidad** - es el punto. Un agente que produce PRs incorrectos no ahorra trabajo, lo crea: el humano tiene que revisar y corregir, que es más caro que hacerlo desde cero.

**Impacto en el sistema real:** el agente prioriza la verificación exhaustiva (contrato público, tests de dependientes, diff review) sobre la velocidad de respuesta. Un issue simple puede tardar 30-60 minutos en producir un PR, en vez de 5-10 minutos si se optimizara para velocidad. El beneficio: la tasa de merge sube (menos PRs rechazados), y el humano confía en el agente para issues de mayor riesgo, lo que a la larga ahorra más tiempo del que "pierde" en latencia.

**El matiz:** la velocidad no se sacrifica en el loop crítico. El planificador determinista (sección 2) y la verificación determinista (sección 3) son rápidos y baratos. Lo que se sacrifica es la velocidad del loop de LLM (el worker de implementación puede iterar más veces antes de dar por bueno un cambio). Es un trade-off de "hacerlo bien a la primera" vs. "hacerlo rápido y corregir después".
