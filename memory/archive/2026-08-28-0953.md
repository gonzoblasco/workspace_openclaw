## ¿Cuál es la API correcta?

Snowystinger dice: *"name those scenarios and add them as we come across them"*. Eso suena a una prop con nombres de escenarios, tipo:

```jsx
<Checkbox focusRing="stretch-to-label">
```

Pero hay un problema: el escenario "stretch-to-label" **requiere** que el label sea `position: relative`. Eso no lo puede controlar el componente Checkbox - es un requisito del consumidor. Entonces la prop no puede ser auto-mágica, necesita documentación.

Mi lectura: la API con **props de estilo explícitas** (`inputStyle`, `visuallyHiddenStyle`) es más flexible y ya cubre todos los escenarios. Pero no es "nombrada".

Una alternativa híbrida sería:
- Mantener las props de estilo explícitas como escape hatch avanzado.
- Agregar una prop semántica para el escenario más común.

Ejemplo:

```jsx
<Checkbox hiddenInput="stretch-to-label">
  {/* requiere position: relative en el label */}
</Checkbox>
```

Esto aplicaría automáticamente el CSS necesario para el escenario A, y cae en las props de estilo explícitas si el usuario quiere otro escenario.

## Sobre la automatización con useLayoutEffect

La idea de snowystinger: detectar si el checkbox ya tiene `position: relative` resuelto y auto-aplicar el stretch.

**Riesgos reales:**
- `useLayoutEffect` corre después del render, entonces el estilo resuelto puede no estar disponible si el padre renderiza condicionalmente.
- Mutar el estilo del input oculto directamente (fuera de React) rompe el modelo mental de React y puede causar problemas con SSR / hydration.
- Si el estilo cambia por fuera del ciclo de React (una librería de CSS-in-JS, un media query, un class toggle), el componente no se entera.
- El `position: relative` podría estar en un ancestro, no en el propio checkbox. `getComputedStyle(checkbox).position` te da el del checkbox, no del contenedor.

**Mi veredicto:** la automatización es interesante para un prop explícito (`hiddenInput="stretch-to-label"`), pero no para un side-effect silencioso. El componente no debería cambiar su layout mágicamente porque el padre tiene `position: relative`.

## ¿Qué proponemos?

Creo que la respuesta a snowystinger debería proponer una API híbrida:

1. **Mantener** `inputStyle`, `inputClassName`, `visuallyHiddenStyle`, `visuallyHiddenClassName` como escape hatch para cualquier escenario.
2. **Agregar** una prop semántica para el escenario "stretch-to-label", que aplique los estilos internamente.
3. **Documentar** claramente que requiere `position: relative` en el label.

## Parte 1: ¿Cuál es realmente el problema que estamos resolviendo?

El problema original (#9687): cuando un usuario con screen reader navega por Checkbox/Radio, el focus indicator del SR se dibuja alrededor del input nativo. Como ese input está dentro de `VisuallyHidden` (colapsado a 1x1px), el ring se ve como un puntito desconectado del componente visual.

No es un bug de react-spectrum en el sentido de "comportamiento roto". Es una limitación de cómo los browsers/SRs dibujan el focus ring: lo hacen sobre el input nativo, no sobre el componente custom. La solución siempre requiere que el input nativo ocupe el área visual.

## Parte 2: Escenarios de uso legítimos

### Escenario 1: "Stretch to label" (el nuestro)
El componente visual es el label. Queremos que el SR ring abrace el label entero.

Requisitos:
- El label debe ser `position: relative` (containing block).
- El wrapper `VisuallyHidden` debe estirarse a `inset: 0`.
- El input debe llenar el wrapper con `position: absolute; inset: 0`.

Este es el escenario más común y el que justifica una prop semántica.

### Escenario 2: "Stretch to button" (CheckboxButton / RadioButton)
En RAC, existe `CheckboxButton` y `RadioButton`. El componente visual es un `<button>`. El input oculto está dentro del button. El SR focus ring ya debería seguir al botón... pero el input sigue siendo 1x1px dentro del button. ¿Importa?

Sí, puede importar: si el botón tiene padding interno o un icono grande, el SR ring podría no coincidir visualmente con el área clickeable. El usuario podría querer estirar el input al botón.

Requisitos similares al escenario 1, pero el containing block es el propio botón (que ya tiene layout propio). Más fácil de aplicar automáticamente.

### Escenario 3: "Custom hit area"
El checkbox está dentro de una card, un row clickeable, o un área mayor. El label solo contiene el texto/checkbox, pero todo el row es clickeable.

Aquí el input oculto necesita cubrir toda la card, no solo el label. Esto ya requiere que el usuario tenga control total del posicionamiento.

Requisitos:
- Posicionar `VisuallyHidden` e `input` con coordenadas arbitrarias.
- Posiblemente usar `inputRef` para asociarlo manualmente (aunque react-aria ya lo hace).

### Escenario 4: "Match visible focus ring"
El componente tiene un visible focus ring custom (outline, box-shadow). El usuario quiere que el SR ring coincida exactamente.

Esto es más difícil porque el SR ring lo dibuja el browser/SR, no el CSS del autor. No podemos controlar directamente el color/grosor del SR ring. Solo podemos controlar el bounding box del input.

### Escenario 5: "No visually hidden input"
En algunos diseños (toggle switch), el input nativo podría querer verse o ser interactivo directamente. Pero eso es otro componente.

### Escenario 6: "Default - do nothing"
Usuarios que no necesitan ajustar el SR focus ring. Debe seguir funcionando como antes.

## Parte 3: Evaluación de APIs posibles

### Opción A: Props de estilo puras (lo que tenemos)
```jsx
<Checkbox
  visuallyHiddenStyle={{ inset: 0, width: 'auto', height: 'auto' }}
  inputStyle={{ position: 'absolute', inset: 0, width: '100%', height: '100%' }}
>
```
- **Pros:** Máxima flexibilidad, cubre todos los escenarios.
- **Cons:** Verbosidad, no es auto-descubrible, el usuario debe saber el truco.

### Opción B: Prop booleana + useLayoutEffect auto-mágico
```jsx
<Checkbox stretchInputToLabel>
```
- **Pros:** Mínima verbosidad.
- **Cons:** Frágil (detectar `position: relative` resuelto), side-effects, SSR risk, no cubre escenarios custom.

### Opción C: Prop semántica con estilos explícitos incluidos
```jsx
<Checkbox hiddenInput="stretch-to-label">
```
- **Pros:** Nombrada, limpia, cubre el escenario común, documenta el requisito.
- **Cons:** Necesita definir qué escenarios soportamos y naming.

### Opción D: API híbrida (mi preferida)
```jsx
<Checkbox hiddenInput="stretch-to-label" />
// o para escenarios custom:
<Checkbox
  visuallyHiddenClassName="custom-wrapper"
  inputClassName="custom-input"
/>
```
- **Pros:** Cubre el escenario común con una prop simple, mantiene escape hatch avanzado.
- **Cons:** Más props, más API surface.

### Opción E: Composición con componente separado
```jsx
<Checkbox>
  <VisuallyHiddenInput layout="stretch-to-label" />
</Checkbox>
```
- **Pros:** Muy explícito.
- **Cons:** Rompe la API actual de RAC, más verbose.

## Parte 4: ¿Qué escenarios vale la pena soportar con prop semántica?

Creo que solo dos escenarios son lo suficientemente comunes y bien definidos:

1. **"stretch-to-label"**: input oculto cubre el label (requiere `position: relative` en el label).
2. **"stretch-to-button"**: input oculto cubre el button (CheckboxButton/RadioButton).

Para el escenario 2, el button ya es el containing block natural. Podríamos aplicarlo sin requisito adicional del consumidor.

Los escenarios custom (card, row, focus ring exacto) los dejamos para las props de estilo explícitas.

## Parte 5: Análisis de la automatización con useLayoutEffect

Vamos a ser técnicos. La idea de snowystinger:

> "if position relative is the resolved style on the checkbox (check in a useLayoutEffect), then we could apply the full height/width automatically"

¿Es viable?

### Problema 1: SSR
En SSR no hay DOM, no hay `getComputedStyle`. El `useLayoutEffect` no corre en el server. Entonces el estilo se aplicaría solo en el cliente, causando potencial flash o hydration mismatch.

### Problema 2: First paint
`useLayoutEffect` corre *después* de que React renderiza pero *antes* de que el browser pinte. En teoría podemos medir el DOM antes del primer paint. Pero si el estilo `position: relative` viene de una librería de CSS-in-JS que inyecta stylesheets asincrónicamente (styled-components, emotion con SSR), puede no estar resuelto todavía.

### Problema 3: Ancestros
El containing block puede ser un ancestro, no el propio checkbox. Si el padre tiene `position: relative` y el checkbox es `position: absolute`, el checkbox no reporta `position: relative`. Pero el escenario "stretch-to-label" requiere que el label sea el containing block. Confundir "checkbox tiene position relative" con "el label es containing block" es un error de diseño.

### Problema 4: Mutación silenciosa
Aplicar estilos al input oculto fuera de React state/props es un side-effect silencioso. Dificulta debugging, testing, y puede romper con futuros cambios de React.

### Veredicto técnico
No recomiendo la detección automática via `useLayoutEffect`. Es demasiado frágil para un beneficio marginal. La prop semántica explícita es mejor.

## Parte 6: Diseño de API recomendado

Propongo:

```jsx
// API propuesta
<Checkbox hiddenInput="stretch-to-label">
```

Naming options:
- `hiddenInput="stretch-to-label"`
- `inputLayout="stretch-to-label"`
- `focusRing="stretch-to-label"`
- `screenReaderFocus="stretch-to-label"`

Me gusta `hiddenInput` o `inputLayout` porque describe *qué* se está posicionando, no *para qué*. El término `focusRing` puede ser confuso porque el focus ring lo dibuja el SR, no nosotros.

### Implementación propuesta

Para `Checkbox`/`Radio` (que renderizan un label interno):
- Cuando `hiddenInput="stretch-to-label"`, aplicar al label `position: relative` y los estilos stretch al `VisuallyHidden` e input.

Pero acá hay un problema: **snowystinger dijo explícitamente que no podemos setear `position: relative` en el label porque sería breaking**. Si la prop `hiddenInput="stretch-to-label"` setea `position: relative` en el label, eso es un cambio de layout.

Alternativa: la prop no setea `position: relative` automáticamente, sino que documenta el requisito. El usuario debe setearlo.

Pero eso reduce la conveniencia de la prop semántica. ¿Vale la pena?

Otra opción: la prop *verifica* en dev mode que el label sea posicionado, y tira warning si no. Pero no setea el estilo.

### Mi conclusión

La API híbrida más segura es:

```jsx
// Escape hatch (ya existe)
<Checkbox
  visuallyHiddenStyle={{ inset: 0, width: 'auto', height: 'auto' }}
  inputStyle={{ position: 'absolute', inset: 0, width: '100%', height: '100%' }}
/>

// Prop semántica para el escenario común
<Checkbox hiddenInput="stretch-to-label">
  {/* user must ensure the label is position: relative */}
</Checkbox>
```

Y agregar una dev-only warning cuando `hiddenInput="stretch-to-label"` está presente pero el label no es un positioned containing block. Eso guía al usuario sin ser breaking.
