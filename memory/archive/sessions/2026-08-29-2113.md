## 1. Modelo de ejecución: single-agent con tool loop + revisor de contexto fresco

**Decisión:** un solo agente ejecutor con tool loop para la secuencia análisis → plan → implementación → verificación, más un segundo agente *solo de revisión* que recibe el plan + diff final sin ver el razonamiento intermedio.

**Por qué no multi-agente de edición paralela:**

- **Latencia:** el trabajo es secuencial por naturaleza. Escribir código en el mismo repo con varios workers paralelos genera conflictos de merge que un humano (o el mismo agente) termina resolviendo, sumando más rondas que las que ahorra.
- **Costo de tokens:** cada worker arranca de cero y necesita el contexto base del repo, convenciones, ADRs, scripts. Un orquestador con N workers paga N × bootstrap. Para tareas de mantenimiento (bugfix, dep bump, backport) rara vez se amortiza.
- **Drift de contexto:** el worker B no sabe qué aprendió el worker A sobre el quirk del build de `pkg-core`. Eso produce "arreglos" que rompen otra cosa.
- **Coordinación:** la edición concurrente obliga a definir ownership por paquete/archivo, y eso rompe cuando un bug cruza paquetes.

**Dónde sí vale la multi-agente:**

- **Revisión con contexto fresco:** un agente revisor que solo ve issue + diff final + resultados de checks. Eso detecta alucinaciones que el autor se autocorrige.
- **Exploración de solo lectura:** buscar archivos relevantes, indexar, comparar APIs entre paquetes. Se puede paralelizar porque no hay locks.

**Qué pasa si un agente falla:**

- El estado vive fuera del agente (git worktree + plan file + progress log). Si el agente muere, otro proceso lo levanta, lee el estado durable y retoma.
- Si el revisor falla, se puede relanzar con un prompt más corto o degradar a self-review del ejecutor con checklist estructurada.

**10× menos tokens:** elimino el agente revisor y uso self-review con checklist de pasos fijos. El ejecutor genera un "informe de confianza" que otro proceso valida mecánicamente.

**10× más tokens:** multi-agente real con especialización (explorador, implementador, tester, revisor) y un orquestador que maneja dependencias entre tareas. Recomiendo esto solo si el monorepo supera ~1 M líneas o si el throughput de issues es muy alto.

## 2. Gestión de contexto: índice jerárquico + lectura bajo demanda con caché de sesión

**Decisión:** no se lee el monorepo completo. Se indexan estructuras estables y se leen archivos bajo demanda, con una caché de sesión que se invalida por hash de commit.

**Qué se indexa (una sola vez por commit base):**

- Grafo de imports y exports por paquete (puede generarse con `typescript`, `ts-morph`, o herramientas como `nx graph` / `turborepo graph`).
- API pública de cada paquete: archivos `index.ts`, `index.d.ts`, exports explícitos.
- Dependencias entre paquetes internos y externas (lockfile + `package.json`).
- Test suites y su cobertura por archivo (mapa "archivo fuente → tests").
- Heurísticos de riesgo: CI workflows, auth, migraciones de DB, cambios de semver.

**Qué se lee bajo demanda:**

- Código del paquete afectado y su grafo de imports upstream/downstream.
- Tests existentes relacionados.
- ADRs, README del paquete, ejemplos.
- Errores concretos de build/test al fallar.

**Cómo se decide relevancia para un issue:**

1. Embeddings del título y cuerpo del issue contra un vector store de archivos (chunks de funciones/clases + path).
2. Grafo de imports expandido: archivos del top-N del embedding + todo lo que importan y todo lo que los importa, hasta 2 saltos.
3. Palabras clave forzadas: si el issue menciona un error, buscar el stack trace; si menciona un paquete, incluir todo ese paquete.
4. "Blast radius": si el archivo cambiado es importado por muchos otros, ampliar el contexto y elevar riesgo.

**Cómo evitar contaminación:**

- El agente no ve outputs de ejecuciones anteriores salvo que sean *resúmenes estructurados* (diff, resultado de check, error corregido). No le pases logs completos de test a la primera etapa de análisis.
- Cada etapa tiene un contexto distinto:
  - Análisis: issue + índice.
  - Plan: issue + archivos relevantes + ADRs.
  - Implementación: plan + archivos editables + tests.
  - Verificación: diff + resultados de checks.
- TTL de caché: la caché de archivos muere si el commit base cambia o si el agente pasa a otra issue.

**10× menos tokens:** embeddings más chicos, chunks más grandes, no se expande el grafo a 2 saltos, solo 1. No se indexa cobertura de tests.

**10× más tokens:** índice más fino (por función, con anotaciones semánticas), recuperación híbrida (BM25 + embeddings + grafo), y un contexto de "memoria del proyecto" persistente entre issues (lecciones de PRs anteriores, estilo del equipo, decisiones frecuentes).

## 3. Verificación y confianza: pipeline de checks + clasificación de riesgo

**Pipeline antes de abrir PR:**

1. `pnpm install` (o equivalente) para asegurar lockfile consistente.
2. Lint + format (`biome check --fix --unsafe .` o `eslint --fix`).
3. Typecheck (`tsc --noEmit` o por paquete).
4. Tests: primero los tests del paquete afectado, luego tests downstream que importan el paquete.
5. Build del paquete afectado y de los que dependen de él.
6. API surface check: comparar exports públicos antes/después (ver si desapareció algo o cambió firma).
7. Verificación semántica: si el issue reporta un error concreto, reproducir el caso mínimo como test nuevo.

**Manejo de falsos positivos:**

- Lint: si una regla falla por código no tocado por el agente, se ignora solo en archivos editados (se restringe el scope). No se permite desactivar reglas globalmente.
- Tests flaky: se marcan como flaky y se requieren 2 pasadas consecutivas antes de considerar verde.
- Snapshot tests: si cambian, el agente debe incluir la diferencia en el informe de confianza; si no están relacionados con el fix, fallan.

**¿Cuándo es "seguro" mergear sin revisión humana completa?**

No se mergea sin revisión en la etapa inicial. Se define un sistema de tiers que se gana con métricas:

- **Tier A (auto-merge elegible):** cambios en docs, fixes de tipos en paquetes internos, patch de dependencia sin cambio de API, todos los checks verdes, archivos tocados solo dentro de `packages/<target>`, sin cambios en CI/workflow/lockfile, diff bajo un umbral (por ejemplo, <100 líneas). Requiere escape rate bajo durante al menos N issues.
- **Tier B (revisión humana rápida):** cualquier cambio en API pública (aunque sea semver-minor), nueva dependencia, cambios en tests, cambios en lockfile.
- **Tier C (nunca autónomo):** publish, modificación de CI, borrado de ramas, force-push, cambios en permisos.

**Detección de alucinaciones:**

- **API diff:** script que compara `exports` y `types` del build contra la versión base. Si aparece una función que no existía o desaparece una firma pública, se bloquea.
- **Contrato downstream:** correr typecheck en los paquetes que dependen del modificado. Si el cambio rompe tipos aunque sus propios tests pasen, se frena.
- **Test de regresión:** todo cambio funcional debe venir con un test nuevo que falle sin el fix y pase con el fix.
- **LLM como linter semántico:** el revisor con contexto fresco recibe el issue + diff y debe responder a "¿este diff resuelve el issue sin introducir APIs inventadas?".

**10× menos tokens:** checks básicos (lint + typecheck + tests del paquete afectado). Sin revisor LLM, sin API diff, sin downstream typecheck. Más riesgo, más dependencia de humanos.

**10× más tokens:** reproducir el entorno del usuario con Playwright/jsdom si aplica, correr tests de integración, generar mutations tests (¿el test nuevo detectaría el bug?), y un segundo revisor semántico.

## 4. Seguridad y límites: tokens divididos, acciones clasificadas, auditoría inmutable

**Decisión:** no hay un solo "token de agente". Se separan credenciales por clase de acción y cada acción destructiva requiere aprobación humana.

**Clases de acción:**

| Clase | Ejemplos | Requiere aprobación |
|---|---|---|
| Read-only | Leer issues, código, logs | No |
| Autónoma reversible | Push de rama feature, abrir PR, commitear en worktree | No (auditable) |
| Destructiva | Borrar rama, force-push, merge, publicar release, modificar CI, acceder a secrets | Sí, explícita, una por acción |
| Secret-touching | npm publish real, `NPM_TOKEN` vivo | Sí + token de corta duración |

**Tokens:**

- **GitHub token:** scope mínimo. Puede leer issues, crear PRs, leer y escribir contenido en el repo objetivo. No puede borrar repos, administrar colaboradores, ni mergear (salvo en un repo sandbox).
- **npm token:** por defecto se usa `--dry-run`. Para publicar real se emite un token de automation/granular con TTL corto (1 hora), scope limitado a `@scope/pkg`, y CIDR allowlist. Solo se mintea si un humano aprobó el release.
- **CI workflow:** el agente no edita `.github/workflows/`. Si detecta que un cambio legítimo requiere tocar CI, genera una sugerencia y pide aprobación.

**Auditoría:**

- Cada tool call del agente se guarda en una tabla append-only: timestamp, issue, tool, args (sin secrets), resultado, hash del estado. No se permite borrar.
- Los secrets nunca se loguean; se reemplazan por placeholders antes de persistir.
- Cada PR abierto incluye un `AGENT-LOG.md` (o metadata en el cuerpo del PR) con el plan, checks corridos, archivos consultados y decisiones del agente.

**Prevención de exfiltración de secrets:**

- El entorno del agente no tiene acceso directo a `~/.npmrc` ni a `.env` del desarrollador. Los secretos se inyectan por un broker que hace masking y valida que el destino sea esperado (por ejemplo, npm registry oficial o GitHub API).
- Egress allowlist: el agente solo puede hablar con hosts necesarios (GitHub, npm registry, registro de telemetry). No navegación libre.
- Los tokens no se pasan nunca como argumento visible en logs; se usan variables de entorno efímeras.

**Loop infinito / daño:**

- **Guard de repetición:** si el agente ejecuta la misma tool con los mismos argumentos y el hash del estado no cambia, se detiene automáticamente.
- **Presupuesto por issue:** límite de tokens, tiempo y cantidad de intentos. Al superarlo, el agente reporta "stuck" y pasa a humano.
- **Sandbox de trabajo:** cada issue usa un git worktree o una copia aislada del repo. El worktree se puede destruir sin afectar el repo principal.
- **Rollback rápido:** si un PR ya mergeado por error genera incidente, un proceso humano o semi-automático revierte con `git revert` y taguea.

**10× menos tokens:** aprobación humana para cualquier acción que no sea read-only. Es más lento pero no se puede permitir un agente barato con poder de escritura libre.

**10× más tokens:** sandbox por VM/contenedor con snapshots, agente de "seguridad" dedicado que revisa cada tool call en tiempo real, y sistema de reputación que reduce aprobaciones solo cuando métricas lo justifiquen.

## 5. Recuperación de fallos: estado durable en 3 niveles

**Decisión:** el estado de cada issue se externaliza en un "job state" que sobrevive a crashes, con checkpoints automáticos.

**Qué se guarda:**

- `issue.json`: issue original, labels, asignee, prioridad.
- `plan.md`: plan de alto nivel con pasos marcables.
- `state.json`: paso actual, commits, PR abierto, hash del worktree base, intentos.
- `context-cache/`: archivos leídos, resultados de checks, diffs intermedios.
- `git worktree`: el repo de trabajo real. Cada checkpoint es un commit (incluso WIP).

**Dónde se guarda:**

- En el filesystem del runner del agente, fuera del repo principal (por ejemplo, `~/.agent-jobs/<issue-number>/`).
- El worktree vive dentro del repo padre (`git worktree add`).
- Copia de respaldo del estado en un storage durable (S3/GCS) si el agente corre en infra volátil.

**Cómo se retoma:**

1. Al arrancar, el agente consulta la cola de issues y el estado de jobs.
2. Si encuentra un job `in_progress` no actualizado hace más de X minutos, lo marca para resumir.
3. Lee `state.json` y `plan.md`, verifica el worktree actual, y ejecuta `git status` para entender qué quedó hecho.
4. Continúa desde el último paso completado. Si el paso actual era "correr tests", los vuelve a correr; si era "abrir PR", verifica si el PR ya existe.

**Anti-duplicación:**

- **Idempotencia de PRs:** antes de abrir un PR, buscar si ya existe uno para ese issue (branch con nombre `agent/issue-N` o label `agent-<id>`). Si existe y está abierto, se actualiza con `git push --force-with-lease` solo si el branch no tiene commits humanos.
- **Branch naming fijo:** `agent/issue-N-<slug>`. No se generan nombres aleatorios.
- **Deduplicación de trabajo:** cada paso guarda el hash del estado; si el hash no cambió entre reintentos, el agente no repite el paso.
- **Rate limit handling:** backoff exponencial con jitter. Si se agota el presupuesto de intentos, pasa a cola humana.

**10× menos tokens:** checkpoints solo entre pasos grandes (plan → implementación → PR), sin context-cache persistente. Menos granularidad, más retrabajo al resumir.

**10× más tokens:** checkpoints en cada tool call con posibilidad de "reproducir" la sesión del agente. Útil para debugging, pero ocupa más storage.

## 6. Métricas y observabilidad: lo que decide si el sistema mejora

**Métricas de outcome:**

- **Tasa de PRs mergeados sin reverts:** el north star. Si sube, el sistema gana confianza.
- **Tiempo medio por issue:** desde que entra a la cola hasta merge o cierre humano.
- **Costo por issue:** tokens consumidos + tiempo de CI.
- **Tasa de escape:** bugs que pasaron todos los checks y aparecieron post-merge.
- **Tasa de rechazo humano:** PRs que un humano cerró o revirtió.
- **Tasa de "stuck":** issues que el agente no pudo cerrar solo y tuvieron que escalar.

**Métricas de proceso:**

- Checks verdes a la primera / después de reintento.
- Cantidad de rondas de revisión.
- Alucinaciones detectadas (API inventada, firma cambiada, test que no prueba el bug).
- Latencia por etapa (análisis, plan, implementación, verificación).

**Cómo usarlas para decidir:**

- Si la tasa de escape es baja en Tier A durante 20-30 issues, se puede ampliar auto-merge.
- Si el costo por issue crece sin que el tiempo baje, revisar la estrategia de contexto.
- Si la tasa de "stuck" sube, probablemente el planificador esté creando tareas demasiado grandes; reducir granularidad.
- Dashboard simple con alertas: escalar si un issue consume >2× el presupuesto promedio.

**10× menos tokens:** solo outcome básico (merge rate, revert rate). Se pierde diagnóstico.

**10× más tokens:** tracing completo por paso, regresión de costo por tipo de issue, análisis automático de "por qué falló" para alimentar el prompt de próximas iteraciones.

## 7. Trade-off final: sacrificaría velocidad antes que seguridad o calidad

**Si tengo que elegir, sacrifico velocidad.**

En un sistema que toca código publicado a npm, con credenciales y reputación del proyecto en juego, un merge rápido mal hecho es mucho más caro que un PR que espera 30 minutos más. La velocidad se recupera con mejores índices, prompts y caché; la confianza perdida por un release roto o un token filtrado no se recupera fácil.

**Impacto concreto:**

- El agente no mergea nunca por defecto.
- La ruta autónoma máxima es "abrir PR y pasar todos los checks". El merge lo hace un humano hasta que métricas lo justifiquen.
- Incluso en Tier A, el "auto-merge" sería un opt-in por paquete, con un periodo de observación.

**Lo que NO sacrificaría:**

- **Seguridad:** tokens mínimos, aprobaciones explícitas, auditoría inmutable.
- **Calidad:** test de regresión, API diff, revisión con contexto fresco. Un agente rápido que genera PRs mediocres aumenta la deuda técnica.

**10× menos tokens:** sacrifico velocidad aún más: aprobación humana casi total, menos contexto, menos rondas de revisión. El sistema pasa a ser "asistente de PR" en vez de autónomo.

**10× más tokens:** no sacrifico velocidad; invierto en infra para mantener seguridad y calidad mientras escalo (sandbox por issue, revisores paralelos, mejor índice).
