# Nivel 1 - Tema 2: Escalabilidad vertical vs horizontal

## Teoría

Cuando tu sistema se queda corto (no aguanta el tráfico, se cae, va lento), tenés dos formas de hacerlo más poderoso:

**Escalabilidad vertical (scale up)** = hacer **una sola máquina más poderosa**. Más CPU, más RAM, más disco. Es "comprar un auto más grande".

**Escalabilidad horizontal (scale out)** = **agregar más máquinas** que trabajan juntas. Es "comprar más autos".

**La analogía (restaurante):**
- **Vertical:** contratás a un chef más rápido, o le das una cocina más grande. Un solo cocinero, pero más capaz.
- **Horizontal:** contratás más cocineros, cada uno con su estación. Varios cocineros trabajando en paralelo.

## La comparación

| | Vertical (scale up) | Horizontal (scale out) |
|---|---|---|
| **Qué es** | Una máquina más grande | Más máquinas |
| **Límite** | Hay un techo físico (no existe máquina infinita) | Casi ilimitado (agregás nodos) |
| **Costo** | Caro, y cada upgrade cuesta más | Más barato por unidad, pagás lo que usás |
| **Complejidad** | Simple (no cambia la arquitectura) | Compleja (necesitás load balancing, distribución) |
| **Falla** | Un solo punto de falla (si se cae, todo se cae) | Redundancia (si uno se cae, los otros siguen) |
| **Cuándo** | Datos que no se pueden partir, o arranque rápido | Sistemas con mucho tráfico, cloud |

## El punto clave (el tradeoff)

**Vertical es más simple pero tiene techo.** Llega un momento en que no podés hacer la máquina más grande (o es ridículamente cara). Es la solución rápida para empezar.

**Horizontal es la que escala de verdad, pero es más compleja.** Necesitás resolver problemas nuevos: ¿cómo distribuyo el tráfico entre las máquinas? (load balancing - lo vemos en Nivel 2). ¿Cómo comparto el estado entre ellas? (si cada máquina tiene su propia memoria, ¿cómo saben todas lo mismo?). Ese "estado compartido" es el dolor de cabeza clásico del scale out.

**La regla de oro:** empezá vertical (simple), y pasá a horizontal cuando el vertical ya no alcanza. No sobre-ingenierices un sistema horizontal desde el día uno si no lo necesitás.

## Práctica (con tu stack)

- **Supabase** escala horizontalmente por vos - cuando crecés, agregás más instancias y un load balancer reparte el tráfico. Vos no te preocupás por eso.
- **Tu app de React** es estática - la servís desde un CDN (escala horizontal: muchos servidores en el mundo sirviendo el mismo archivo estático).
- **La base de datos** es donde el scale out se complica - porque el estado (los datos) tiene que ser consistente entre todas las máquinas. Por eso PostgreSQL escala vertical primero (una máquina grande) y recién después horizontal (sharding, replicación - lo vemos en Nivel 3).

## Errores comunes

1. **Ir a horizontal demasiado pronto** - agregás complejidad (load balancing, estado compartido) cuando un upgrade vertical te hubiera alcanzado. Sobre-ingeniería.
2. **Pensar que horizontal es gratis** - no lo es. Cada máquina extra trae problemas de coordinación.
3. **No entender que la DB es el cuello de botella** - podés escalar horizontalmente tus servidores de app todo lo que quieras, pero si la base de datos no escala, ahí se te junta todo.

## Tema 3: CAP theorem

Este es el concepto que más se cita en entrevistas de diseño de sistemas, y el que más se malentiende. Vamos a hacerlo bien.

## Teoría

CAP es un teorema que dice que **un sistema distribuido** (varias máquinas trabajando juntas, como la opción B de la mini-pregunta) **no puede garantizar las tres cosas a la vez**. Tenés que elegir dos de tres:

**C = Consistency (Consistencia)** - todos los nodos ven los mismos datos al mismo tiempo. Si escribís en un nodo, todos los demás lo ven inmediatamente.

**A = Availability (Disponibilidad)** - el sistema siempre responde, siempre está disponible. Cada request recibe una respuesta (aunque sea con datos viejos).

**P = Partition tolerance (Tolerancia a partición)** - el sistema sigue funcionando aunque se corte la comunicación entre nodos (una red se cae, un nodo se desconecta).

## El punto que casi todos se equivocan

**No podés elegir cualquiera de las tres - la P es obligatoria.** En un sistema distribuido, las particiones (cortes de red) van a pasar, es inevitable. Así que en la práctica solo elegís entre **C y A**: cuando hay una partición, ¿preferís que el sistema siga respondiendo con datos posiblemente viejos (A) o que se niegue a responder hasta asegurarse de que los datos son correctos (C)?

**La analogía (dos cajeros de un banco conectados por un cable que se corta):**
- Un cliente deposita en el cajero A. El cable al cajero B se corta.
- **Si elegís Consistencia (C):** el cajero B se niega a dar información hasta que se reconecte y sepa el saldo real. Prefiere no responder a responder mal.
- **Si elegís Disponibilidad (A):** el cajero B sigue respondiendo, pero puede dar un saldo viejo (sin el depósito que se hizo en A). Prefiere responder (aunque sea con datos viejos) a no responder.

## Los dos polos prácticos

- **CP (Consistencia + Partición):** sistemas donde los datos tienen que ser exactos siempre. Ej: sistemas de pagos, bancos. Prefieren no responder a responder mal.
- **AP (Disponibilidad + Partición):** sistemas donde es mejor responder siempre, aunque sea con datos un poco viejos. Ej: redes sociales, feeds, carritos de compra. Prefieren responder a no responder.

## Práctica (con tu stack)

- **Supabase/PostgreSQL** es típicamente **CP** - prefiere consistencia. Si hay un problema de red, prefiere esperar a estar seguro que darte datos incorrectos.
- **Un feed de redes sociales** (Instagram, X) es **AP** - si el servidor no puede confirmar el dato más nuevo, te muestra lo que tiene (quizá un poco viejo) en vez de no mostrarte nada.

## Errores comunes

1. **Decir "elegís dos de tres" sin aclarar que P es obligatoria** - el entrevistador te va a corregir. La P no se elige, se asume.
2. **Confundir consistencia con "los datos son correctos"** - consistencia en CAP es "todos los nodos ven lo mismo", no "el dato es verdadero".
3. **Pensar que es una elección binaria permanente** - muchos sistemas son CP en algunas operaciones y AP en otras. Un carrito de compra puede ser AP para ver el catálogo y CP para el pago.
