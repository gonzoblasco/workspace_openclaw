## Contexto del problema

Estás migrando una SPA React (50 componentes, Context API para estado global, 10 REST endpoints) a Server Components de Next.js 16 con streaming, **sin downtime**, con 2000 usuarios activos y picos de 500 concurrentes.

Puntos que definen la complejidad real:
- **Sin downtime** → no es una reescritura, es una **migración incremental** (la parte más difícil, y la que casi nadie cubre bien).
- **500 concurrentes** → el streaming y los Server Components cambian dónde se paga el costo de render; hay que pensar en caché y en qué se renderiza en server vs client.
- **Context API global** → es la fricción arquitectónica más grande. Context es un patrón de cliente; no sobrevive el salto a RSC tal cual.

## Mi recomendación concreta (lo que el Nivel 4 debería incluir como plan ejecutable)

**1. No migres todo. Migrá por rutas con feature flags.**
Cada ruta de la SPA se convierte en una ruta de Next.js que puede renderizar versión vieja (client) o nueva (server) según flag. Rollback = apagar flag, no redeploy.

**2. Atacá el Context API primero.**
Es el bloqueante real. Estrategia:
- Lo que es **estado de servidor** (datos del usuario, permisos, settings) → sale de Context, va a server components + props serializadas + `cache()` de React 19.
- Lo que es **estado de UI** (tema, sidebar abierto, modales) → se queda en Context pero **solo en client components**, con el provider envuelto lo más abajo posible (evitá que el provider abrace server components y fuerce `'use client'` en todo el árbol).
- Mutaciones → Server Actions con `useActionState` + `use optimistic`.

**3. Streaming como estrategia de percepción, no solo de velocidad.**
Cada ruta nueva: `loading.tsx` (skeleton estático) + `Suspense` boundaries en las secciones lentas. El usuario ve contenido inmediato mientras el server streamea el resto. Con 500 concurrentes, además, esto distribuye mejor la carga porque no esperás el render completo en el server.

**4. Rollout con canary + métricas.**
- 10% de tráfico → nueva versión, medí TTFB, INP, error rate vs baseline.
- Solo subís a 100% si las métricas no empeoran.
- Verificás en producción, no en tu máquina: 500 concurrentes no se reproducen local.

**5. Testing en dos capas.**
- Unit/integration: los server components se testean con React Testing Library igual que antes (la API cambia poco).
- E2E: Playwright con las **mismas specs corriendo contra ambas versiones** (flag on/off) para garantizar paridad funcional. Sin paridad E2E no hay migración segura.
