## 1. Modelo de ejecución: single-agent vs multi-agente

The honest answer: **single-agent with tool loop for the common case, with a narrow, well-defined sub-agent fan-out only for parallelizable read-only work**. Not a full multi-agent hierarchy.

Trade-offs:
- **Latencia:** multi-agent parallelizes (analyze multiple packages in parallel, run affected-package tests in parallel). But coordination overhead adds serialization points. Single agent is sequential but each step is predictable.
- **Costo de tokens:** multi-agent duplicates context. Every worker needs its own bootstrapping (repo structure, conventions, tooling). An orchestrator that delegates N subtasks pays N × context bootstrap. Single agent builds up context once and reuses. For a maintenance agent where tasks are mostly small-medium (fix bug, update dep, backport), the fan-out cost rarely pays off.
- **Drift de contexto:** multi-agent workers don't see each other's intermediate reasoning. Worker B doesn't know what Worker A learned about the quirk in pkg-core's build config. With single agent, everything learned stays in context. Mitigation in multi-agent: structured handoffs, but that's more machinery.
- **Coordinación:** merge conflicts between parallel workers editing the same repo. If two workers both touch packages/core, you get a mess. Single agent = single writer, conflicts are impossible by construction.
- **Failure modes:** single agent dies → task dies, but state is checkpointed (section 5). Multi-agent: partial failures are worse - worker A succeeded, worker B produced garbage, orchestrator must reconcile. Reconciliation logic is the hardest part of multi-agent systems and the usual source of "the fix introduced a new bug" (his own lesson: cross-review can INTRODUCE bugs).

Key domain insight: **code changes are inherently serial** - one working tree, one git history. Parallel read-only analysis is safe to fan out; parallel writes are not. So: the architecture is "one writer, many readers." 

Concretely per issue:
- Triage + planning: the orchestrator (single agent, thinking max)
- Read-only recon CAN be subagent-fanned (e.g., "which of the 14 packages import this deprecated API" - parallel greps/dep-graph queries)
- Implementation: single agent, single writer
- Review: a SECOND agent with fresh context (no contamination from the implementer's assumptions) - this is his A/B pipeline pattern, validated in his own setup. Cross-review with the caveat he learned: reviewer verdict isn't trusted, verification is against real sources (the actual API), not the reviewer's word.

So the answer is: "single-agent core with task-scoped ephemeral sub-agents for read-only parallelism and one independent reviewer." Not a flat multi-agent swarm, not a strict hierarchy.

When would multi-agent win? If tasks were long-running and independent (e.g., migrating 14 packages independently to a new linting config). Then fan out one worker per package with clear ownership boundaries. Note that as a bounded exception: bulk migrations, only with per-package path ownership to avoid write conflicts.

10x tokens less: single agent only, no sub-agents at all, smaller model for triage, skip the reviewer agent (rely on CI + checklist). 10x more: still single writer (more parallelism doesn't help writes), spend budget on the recon fan-out and on the independent reviewer with bigger context, plus a "second opinion" on risky changes.

## 2. Gestión de contexto

200k+ lines can't be read. Strategy layers:

**Index (built once, refreshed on main):**
- Repo map: packages, their public entry points, exports, dependency graph (internal + external), tsconfig project references. Generated from tooling, not from reading code: `tsc --listFiles`, package.json workspaces, tsup/rollup entry analysis, `npm ls`. This is a STRUCTURED artifact (JSON), maybe a few thousand tokens for the whole map.
- Per-package API surface: exported symbols with signatures - extractable with ts-morph/API extractor. This is the key artifact for maintenance: it lets the agent know the public contract without reading implementations, and it's the basis for contract-break detection (section 3).
- CI/test matrix: which packages have tests, what commands run.
- Conventions doc (AGENTS.md at root + per-package notes).

**On-demand reading:**
- Issue → relevance decision. The issue text gives entity names (package names, component names, error messages, stack traces). Resolution strategy: symbol search in the API-surface index → jump to package → read the files that own the failing symbols (owners via CODEOWNERS or import graph).
- Start from the stack trace / failing test name, walk up the import graph, not down. Reading callers tells you the contract; reading callees tells you implementation. For a fix, you usually need contract-first, then implementation.
- Budget: e.g., hard cap per phase. Plan phase: index + issue + targeted greps only (no full file reads unless small). Implement phase: full reads of the 3-10 files that matter + tests around them.

**Anti-contamination (stale context):**
- Never persist working context between issues. Every issue starts fresh from the committed index, not from previous session's memory. (His own rule: sessions per project; here: session per issue.)
- Index freshness: index is regenerated from main HEAD when the task starts (or versioned by commit SHA; if the SHA it was built on is more than N commits behind the working base, regenerate the sections touched). Stale index is the #1 source of "agent edits a line that doesn't exist anymore."
- File reads are always current-state reads (re-read after any self-made edit before further edits; the edit-apply result is the truth, not what the agent remembers). Actually for the agentic loop with tools, file edits return the new state - treat tool results as ground truth over the agent's memory.
- Grep-first culture: prefer targeted `grep`/symbol search over opening directories. Don't let the agent "explore" by reading folders - that's how context fills with irrelevant code. Exploration budget with a rule: if after K lookups the agent can't localize the relevant files, it must come back with a plan question rather than reading more. That's a drift guard.

**Deciding relevance for an issue:**
1. Parse issue: extract package names, exported symbols, error strings.
2. Lookup in index (symbol → package → files).
3. If ambiguous (name collisions, symptom could come from 2 packages), do a cost-ordered probe: grep for the error string in the failing test / user report first - cheapest disambiguator.
4. Relevance confidence: if the top candidate doesn't reproduce (failing test, unit repro, or trace match), stop and ask/comment on the issue with the hypothesis. Don't let low-confidence relevance turn into shotgun edits.

10x less budget: index only package.json graph + README-level knowledge; everything else grep-on-demand; smaller excerpts on read (offset/limit). 10x more: richer index (per-file summaries embedded, semantic search over code chunks), plus a persistent "issue→files touched" history to learn which parts of the repo churn together.

## 3. Verificación y confianza

Pipeline before PR:
1. **Typecheck** per affected project (tsc project references / turbo affected). Catches nonexistent exports/imports = hallucinated API detection at the first line of defense. `tsc` is the API existence oracle.
2. **Unit tests** affected packages (vitest changed-files strategy) → full suite before PR.
3. **Lint + format** (Biome).
4. **Build** all affected packages (ensures bundlers resolve, types emit cleanly).
5. **Contract check (API diff):** run api-extractor / api-extractor-model or ts-morph export diff against the previous published version's surface. Breaking = removed/renamed/re-typed export in a published package. This is deterministic, not LLM-judged. If breaking + semver major not requested → block and comment.
6. **Behavioral smoke for public contracts:** for each touched package, run its public-import test (a test file that imports only from the package entry point, like a consumer would). Cheap and catches "works internally, breaks externally."

**Hallucination detection specifics:**
- tsc catches nonexistent symbols/exports as compile errors. Nonexistent *runtime* APIs (a lib method that exists in docs but not in the installed version): check version pinning - if the agent used an API, grep the .d.ts of the installed dep; optionally a rule: any import of a dep API must resolve in node_modules types. That IS tsc. The sneaky case: APIs that exist but are deprecated/unsafe - lint rule + api-report annotations.
- Another sneaky one: invented config options (e.g., a `tsconfig` flag that doesn't exist) - again tsc/JSON-schema validation catches.
- The non-deterministic residue: the fix *logic* being wrong in a way that compiles and passes written tests. Guard: agent must write/adjust a failing-test-first repro for the actual issue. A fix without a red→green test is rejected. (His incremental-implementation skill: verify implementation, not just text.)

**False positives handling:**
- Flaky tests: maintain a known-flaky quarantine list; a failing test that's on the list doesn't block, but is reported; two consecutive flaky reports → auto-open an issue to fix/stabilize. Never let flake justify "retry until green" - bounded retries (1) with distinct output analysis, then quarantine.
- Type errors introduced by generated files/stale builds: deterministic re-run after `clean` once.
- If CI fails in a way the agent can attribute to pre-existing main breakage: verify by running the same check on untouched main SHA; if main is red, the agent comments and stops rather than "fixing" unrelated things.

**When is it safe to merge without full human review?** Tiered autonomy:
- Tier A (auto-merge eligible): docs/typefixes/deps patch in internal packages, API diff clean (no surface change), all checks green, no files outside `packages/<target>` touched, no CI/workflow/lockfile changes, change size under threshold (e.g., <100 diff lines). 
- Tier B (single human review): any public package API change (even semver-minor), new dependency, test-only changes (tests define truth - a PR that both breaks and fixes tests must be reviewed), lockfile changes.
- Tier C (never autonomous): publish, CI changes, destructive git ops.
- Calibrated opening: start with Tier A limited to ONE package, measure escape rate (bugs that passed auto-merge), expand per-package as escape rate stays at 0 over N PRs. Trust is earned per scope, not granted globally. (This mirrors his a11y PR validation lesson: automated checks pass ≠ visual/real-world correct - for UI packages, add a tier rule: UI visual changes always Tier B.)

## 4. Seguridad y límites

Permission model:
- **Least privilege, split tokens:** npm publish token and GitHub token are NOT the same credential and never live in the agent's runtime env simultaneously. GitHub token: contents:write + PRs only on this repo, no admin. npm: `--dry-run` by default; real publish is a separate short-lived token (automation/granular token, 1h TTL) minted only at publish time, and only if a human approved the release.
- **Action classes:**
  - Read/analyze: free.
  - Write in working tree + branch push + PR open: autonomous (auditable, reversible via git).
  - Destructive (branch delete, force-push, release publish, CI workflow modification, secret access, adding collaborators): human approval, explicit, per-action. Approval is bound to a diff: the human approves THE TEXT of the change, not a vague "allow workflow edit."
- **CI modification is a hard rule:** workflow files are executable code with secrets access. Any diff touching `.github/` → Tier C. The agent literally cannot merge its own CI change; a branch protection rule + CODEOWNERS requiring a human reviewer on `.github/**` enforces this server-side (agent self-restraint is not enough - enforce in GitHub).
- **Audit:** every action appends to an append-only audit log (structured JSON): timestamp, task id, action, inputs hash, outcome. Git itself audits code changes. Shell commands run by the agent get logged with argv (his pipeline already logs; formalize). Audit log ships out of the agent's sandbox (can't edit its own trail).
- **Exfiltration prevention:**
  - Network egress allowlist from the agent runtime: npm registry, GitHub API only. No general internet. (Blocks "post secrets to pastebin".)
  - Secrets never enter the model context: tokens live in env of specific tool processes, never in files the agent reads, never in prompts. Masking layer on tool outputs + a scan before any outbound text (PR body) for secret-like patterns (his safe-fetch concept, inverted: check outbound, not just inbound).
  - PR bodies/issues comments: same outbound scan.
- **Runaway/loop control:**
  - Global budget per task: max steps, max tokens, wall-clock, max cost in $. Exceeded → task pauses, human-notified, no silent retry loops.
  - Loop detector: same tool call with same args twice in a row without state change → hard stop. Repeated failing check > N with same error → stop escalating, report.
  - Resource guards: process timeouts, no background daemons, workspace disk quota.
  - Kill switch: a single command/file flag that suspends the agent; when paused, it holds locks and stops starting new tasks. (July 2026 incident shape: autonomy without budgets.) His ADR-007 principles: fast feedback loops, explicit tool limits, human-in-the-loop for destructive actions, full logging - this section is ADR-007 applied.
- **Isolation:** agent runs in dedicated workspace/VM (or at minimum, dedicated user), with its own git clone; does not run on the human's laptop session with their cookies. Destructive commands physically require the approval channel, not just policy prompts the model can talk itself around.

10x less: fewer models, but security items are non-negotiable (they're not token-costly anyway - egress allowlist and split tokens are infra). 10x more: add automated security review agent on each PR (semgrep etc.), more exhaustive secret-pattern scanning, still require human for Tier C.

## 5. Recuperación de fallos

- **State store:** one durable task record per issue, keyed by issue number, in the orchestrator's store (SQLite or a state file per task in a dedicated directory, e.g., `state/tasks/<issue>.json` + artifacts dir). Contains: phase (triage/plan/implement/verify/pr), plan, files touched, branch name, last completed step, next action, token/cost counters, timestamps. Every phase transition = checkpoint BEFORE starting the risky work (write-ahead: record intent before acting). (He literally has pipeline-track.sh for this in his own pipeline - "estado durable... sobrevive a SIGKILL/restarts (crash recovery)". Same pattern.)
- **Idempotency for resume:** each step designed as idempotent where possible: re-running "checkout branch X" is safe; "apply patch" is guarded by checking diff-state first.
- **Git as ground truth:** branch + commits are the real checkpoint. Commit early, commit often (per green test run): a crash mid-task loses at most the last slice.
- **Dedup (no duplicate PRs):**
  - Claim protocol: task record created at triage with `status: claimed` before any work; a unique branch naming scheme `<issue>-<slug>` deterministic from issue number (not from title/retry count) - recomputing it always yields the same name.
  - Before starting work: check remote for existing branch/PR linked to issue (GitHub search: PRs referencing issue, branches by exact name). If found → resume that PR, never open a second.
  - PR creation is guarded: search first, create second; and GitHub-side, the issue has a label like `agent:in-progress` set at claim and cleared at terminal state - orchestrator refuses tasks with that label unless the state store says it's dead (stale > X hours with no commit activity → reclaim allowed).
  - Exactly-once-ish for side effects: PR/publish/comment actions get an idempotency key = (issue, action, content-hash); the log is checked before firing.
- **Crash types:** SIGKILL mid-exec → on restart, orchestrator reads state, verifies working tree against last recorded commit, discards uncommitted garbage from dead run (or commits it to the branch as WIP if structurally sound), continues. Rate limit/timeout → backoff with cap, resume same state. Corrupted state (partial write) → state files written atomically (temp + rename, he knows this pattern from file_write).
- **Retries vs human:** 2 automatic resume attempts per failure class; then park the task with a diagnostic comment on the issue. No infinite retry (links to section 4 loop guards).

## 6. Métricas y observabilidad

Core metrics, per PR/task:
- **Success rate:** % of opened PRs merged without human code edits (human touched-after ≠ pure merge), % abandoned, % reverted after merge. The real KPI: **merged-without-human-modification rate** and revert rate. Merged-then-reverted is the worst outcome - it means checks were insufficient.
- **Escape rate:** bugs found in merged agent PRs (by issues referencing them within 30 days). This is the trust currency for expanding Tier A scope.

- **Quality-of-process:** check-pass rate on first try (typecheck green first attempt = proxy for grounding quality), test red→green discipline compliance, % tasks where the agent asked a clarifying question vs. went ahead wrongly.
- **Review load:** median human review time on agent PRs vs human PRs (if agent PRs take longer to review, something's wrong with PR readability - description quality is a metric too).

Instrumentation: the audit log (section 4) IS the event stream; dashboards per phase; weekly rollup that compares windows (last 50 tasks vs previous 50) rather than cumulative averages - trends, not totals.
Decision rules wired to thresholds, e.g.: escape rate > 2% in last 50 merged PRs → tighten tiering automatically (revert to Tier B everywhere), investigate top failure classes; first-try typecheck rate dropping → index drift suspected → regenerate index more often.
Cost per issue tracked against the value proxy (issue severity label). Not "cheapest" but $ per successfully merged fix.

The honest part: measure, don't vibe. Every system of this kind drifts with model updates, dep updates, prompt rot - metrics are how you notice. Also track "distribution shift" triggers: new package added → treat first 20 PRs in it as Tier B.

## 7. Trade-off final

Which to sacrifice: this is the spicy question. Options: velocidad, costo, seguridad, calidad.

My answer: **velocidad** - con matices. Rationale: 
- Seguridad can't be sacrificed (irreversible damage, trust, credentials, July-2026-incident shape). Calidad can't be sacrificed (low-quality agent PRs cost MORE human time reviewing/fixing than doing the work manually - the agent's entire value proposition is net time saved with quality ≥ bar; a fast wrong agent is a negative-value agent). Costo has a floor but scales with usage and is bounded by budgets - sacrificing cost means slower iteration but doesn't break the system.
- Velocidad is the only one with a graceful degradation: an agent that takes 2h per issue instead of 20min still works - issues are async by nature, the queue absorbs latency. Autonomy's value is in removing human latency, not in agent-internal speed. A slow-but-right PR beats a fast-wrong one every time: reviewers batch, humans check once a day.
- Concretely what sacrificing speed buys: fewer, more expensive verification passes (two independent reviewers, full test suite not affected-only, longer context for the implementer, more careful plans with step-back points). With generous budgets you run serial verification; with time pressure you cut corners - cut time, not corners.
- Impact on the real system: PRs land slower → issues queue up more → need priority triage; SLA per severity class; the batch efficiency actually goes UP (agent can work while human sleeps - overnight runs). The thing velocity-buying protects is only the interactive case ("fix it while I watch"), which is the minority use for a maintenance agent.

Counter-case to be honest about: if the deployment were a hotfix pipeline (production incident), speed ranks higher and you'd pre-authorize fast paths. Acknowledge that the sacrifice is context-dependent; for a maintenance monorepo agent, async correctness > latency.

# Arquitectura: Agente de Mantenimiento para Monorepo TS Publicado

## 1. Modelo de ejecución

**Decisión: núcleo single-agent con tool loop (un único "writer"), sub-agentes efímeros solo para lectura paralela, y un revisor independiente (patrón A/B) con contexto fresco.** No un enjambre multi-agente.

La razón estructural: los cambios de código son inherentemente seriales. Un working tree, un HEAD. Dos writers al mismo repo es una carrera por la construcción; la paralelización segura es la de **lectura**, no la de escritura. El fan-out de workers que escriben es el caso donde multi-agente promete más de lo que entrega.

| Dimensión | Single-agent + loop | Multi-agente (orquestador + workers) |
|---|---|---|
| Latencia | Secuencial pero predecible; los tests ya paralelizan solos | Paraleliza lectura, serializa en el orquestador; el sync overhead se come parte de la ganancia |
| Costo de tokens | El contexto se construye una vez y se reutiliza | N × bootstrap por worker (estructura del repo, convenciones, tooling) + costo de handoffs |
| Drift de contexto | Mínimo: todo lo que el agente aprende queda en un hilo | Alto entre workers; mitigable solo con handoffs estructurados, que es más máquina |
| Coordinación | Trivial por construcción | Merge conflicts entre workers, locking de archivos, reconciliación de resultados parciales |
| Fallo | Muere la tarea entera, pero con checkpoint + resume (sección 5) es recuperable | Fallos parciales: A dejó cosas bien, B dejó basura; reconciliar ese estado mixto es la fuente clásica de "el fix introdujo un bug" |

El punto de falla único del single-agent se paga con la sección 5 (estado durable), no con más agentes. Tu propia experiencia con el pipeline A/B valida las dos partes: el cross-review vale (B agarra cosas que A no ve), pero el veredicto de B no se confía, se verifica contra la fuente real, y B puede introducir bugs "corrigiendo" código correcto.

**Excepción acotada:** migraciones masivas (migrar 14 paquetes a una nueva config de lint) sí justifican un worker por paquete, con ownership de paths explícito (cada worker solo puede tocar `packages/<su-paquete>/**`) para que la paralelización no genere conflictos. Es la única forma de multi-agente por escritura que apruebo: partición de dominio, no coordinación.

Pipeline por issue: triage (modelo chico, classify + claim) → plan (single agent) → recon opcional en fan-out (sub-agentes read-only: impacto vía import graph, quién usa esto) → implementación (single writer, commit por slice verde) → verificación (sección 3) → revisor B independiente → PR.

**Con presupuesto 10x menor:** single agent puro, sin sub-agentes, sin revisor (CI + checklist humano en vez de agente B), triage con modelo local chico.
**Con 10x mayor:** el writer sigue siendo uno (más paralelismo no ayuda a la escritura); el presupuesto extra va a recon fan-out más profundo y al doble review de cambios riesgosos.

Fix sin evidencia ro→verde no abre PR. El revisor B lee el diff de tests con prioridad (si "arregló" los tests para que pasaran, es revisión obligatoria).

**Detección de contrato público roto:** api-extractor (o diff de superficie con ts-morph) entre la última versión publicada y la propuesta. Export eliminado, renombrado o retipeado = breaking detectado **por código, no por juicio del modelo**. Breaking sin major pedido → bloqueo + comentario con el diff de superficie. Además del typecheck, cada paquete tocado corre un test de "consumidor": un archivo que importa solo desde el entry point público, como lo haría un usuario. Cacha el clásico "andaba internamente, rompía afuera".

**Falsos positivos:**
- Tests flakers: lista de quarantine. No bloquean, se reportan; dos reportes seguidos del mismo test → issue automático de estabilización. Prohibido el retry-until-green: máximo 1 reintento y solo si el output del fallo es distinto; si no, park.
- Falla preexistente en main: si el mismo check falla en el SHA de main puro, no es del agente: comentario en el issue + park. Jamás "arreglo de paso" cosas no relacionadas (el scope creep es un riesgo de calidad, no una cortesía).

**Autonomía graduada (cuándo se mergea sin revisión completa):**

| Tier | Alcance | Regla |
|---|---|---|
| A (auto-merge) | Docs, fixes de tipos, deps patch en paquetes internos; superficie intacta, todo verde, diff < ~100 líneas, sin tocar lockfiles ni CI ni otros paquetes | Se habilita por paquete, empezando por UNO |
| B (1 revisión humana) | Cualquier cambio de superficie pública (incluso minor), deps nuevas, lockfile, cambios de tests, cambios visuales de UI | Siempre |
| C (nunca autónomo) | Publish, CI, operaciones destructivas de git | Server-side enforced (sección 4) |

La expansión del Tier A se decide por evidencia: con tasa de escape 0 en N PRs de un paquete, ese paquete escala a Tier A. La confianza se gana por scope, no se declara por optimismo. Y aplicando tu lección del PR de react-spectrum: los checks automatizados no reemplazan el ojo humano en visuales; eso queda clavado en Tier B.

**10x menor:** solo checks 1 a 4, API-diff manual en Tier B, suite completa solo al final, Tier A reducido a docs.
**10x mayor:** doble revisor independiente, property/fuzz testing sobre contratos públicos, security scan (semgrep) por PR, mutation testing puntual en paquetes críticos.

# 4. Seguridad y límites

**Decisión: credenciales divididas, permisos por clase de acción, auditoría fuera del sandbox, y todos los límites "duros" forzados por infraestructura.**

- **Credenciales separadas:** token GitHub de scope mínimo (contents:write + PRs, solo este repo, nada de admin). npm: token granular de vida corta (~1h), minteado solo después de que un humano apruebe la release concreta, inyectado únicamente al proceso del paso de publish. Nunca ambos viven juntos en el ambiente del agente.
- **Clases de acción:** lectura libre. Escritura en working tree + push de rama + abrir PR: autónomo, porque es auditable y reversible por git. Destructivo (borrar rama, force-push, publish, tocar CI, acceder secrets): aprobación humana explícita **ligada al diff exacto**: se aprueba el texto del cambio, no un permiso genérico.
- **Regla dura de CI:** cualquier diff en `.github/**` es Tier C, forzado server-side: CODEOWNERS sobre `.github/**` + branch protection + un workflow que falle si el autor es el bot sin approver humano. El agente no puede mergeear su propio cambio de CI ni con la aprobación entusiasta de su propio pipeline. La contención del modelo no es contención.
- **Auditoría:** log append-only estructurado (taskId, acción, hash de inputs, resultado), escrito fuera de la sandbox del agente: no puede editar su propia pista. Git audita el código; el log audita las acciones.
- **Anti-exfiltración:** allowlist de egress (registry npm + API de GitHub, nada más; bloquea el "posteo las credenciales a un pastebin"); los secrets nunca entran al contexto del modelo (viven en el env de procesos tool específicos); scan pre-envío de todo texto saliente (body del PR, comentarios) buscando patrones de secretos, enmascarado en outputs de tools.
- **Anti-runaway:** presupuesto por tarea (pasos, tokens, dólares, wall clock) con corte duro y notificación al humano; detector de loop (misma llamada con mismos args dos veces sin cambio de estado → stop; mismo error más de N veces → park con diagnóstico); timeouts en cada proceso; kill switch que congela todo.
- **Aislamiento:** runtime dedicado (usuario/contenedor propio, clone propio, disco acotado). Nunca el entorno del humano con sus cookies. Esto es ADR-007 aplicado: límites explícitos en las herramientas, human-in-the-loop en lo destructivo, logging completo. El incidente de julio 2026 fue exactamente la ausencia de estos frenos.

**10x menor:** todo esto se mantiene igual. La seguridad es infraestructura, no tokens; recortarla es la peor economía posible del sistema.
**10x mayor:** security review automático por PR, análisis de comportamiento en sandbox, scanning más exhaustivo. Tier C sigue cerrado igual.

# 5. Recuperación de fallos

**Decisión: el estado dura en dos capas, git como checkpoint real y un registro por tarea write-ahead, con protocolo de claim que hace imposible el PR duplicado.** Es el mismo patrón que ya validaste con `pipeline-track.sh`: estado durable que sobrevive SIGKILL y restarts.

- **Registro por tarea:** `state/tasks/<issue>.json` más un directorio de artifacts. Campos: fase actual (triage/plan/implement/verify/pr), plan, branch, próximo paso, contadores de costo, timestamps, último commit verificado. Write-ahead: se registra la intención **antes** del paso riesgoso, con escritura atómica (temp + rename, sin estados corridos a la mitad).
- **Git como checkpoint:** commit por slice verde. Un crash a mitad pierde como mucho el último slice, nunca la tarea.
- **Idempotencia por construcción:** branch determinística `<issue>-<slug>` derivada del número del issue (no del título, no del intento): recalcularla siempre da el mismo resultado. Nada crítico depende de "corrió una sola vez".
- **Protocolo anti-duplicación:** al triage se marca la tarea como `claimed` y se pone el label `agent:in-progress` en el issue, antes de trabajar. Antes de empezar: buscar PR o rama existente vinculada al issue; si existe, se hace resume de ese PR, jamás se abre otro. La creación de PR es search-then-create con idempotency key (issue, acción, hash de contenido). Label stale (muchas horas sin commits) → se permite reclaim, previa verificación del estado de la rama remota.
- **Reintento acotado:** 2 reanudaciones automáticas por clase de fallo (crash → resume desde la fase registrada, verificando el working tree contra el último commit y descartando basura; rate limit → backoff con tope; estado corrupto → re-verificar y reconstruir). Agotado el cupo: park con comentario diagnóstico en el issue. El reintento infinito se corta por diseño y conecta con los presupuestos de la sección 4.

**10x menor:** JSON + commits, y el resume re-ejecuta la fase actual con un paso previo "verificar estado real antes de continuar".
**10x mayor:** event-sourcing completo de las acciones del agente (reproducible paso a paso), ejecute especulativo de pasos flaky, retry A/B con modelo distinto ante fallo repetido.

# 6. Métricas y observabilidad

**Decisión: la métrica de verdad es "merged sin modificación humana y sin revert", y la confianza se expande por escape rate medido, no por sensación.**

En orden de jerarquía:
1. **Tasa de PR mergeados sin edición humana** y tasa de revert post-merge. El revert es el peor resultado: significa que todos los checks fueron insuficientes.
2. **Escape rate:** bugs reportados en 30 días contra PRs del agente. Es la moneda de la confianza: regula la expansión de Tier A (sección 3).
3. **Eficiencia:** costo por issue (tokens/dólares por fase), wall clock por fase, número de intervenciones humanas por tarea.
4. **Salud de proceso:** first-try pass rate de typecheck/tests (proxy de grounding: si baja, el índice está obsoleto o los prompts se deterioraron), % de PRs con evidencia ro→verde, latencia de revisión de PRs del agente vs los humanos (si los del agente tardan más en revisarse, el problema es la calidad de la descripción, y eso también es una métrica).

**Cómo se usan:** comparación por ventanas (últimos 50 tasks vs 50 anteriores), nunca promedios acumulados que esconden tendencias. Reglas cableadas a umbrales: escape rate > 2% en 50 PRs → tightening automático a Tier B global + análisis de clases de fallo; first-try en baja → regeneración de índice más frecuente; costo etiquetado por severidad del issue (no se optimiza "el más barato" sino dólares por fix correcto). Trigger de drift estructural: paquete nuevo o refactor grande → los primeros 20 PRs de ese scope van a Tier B sea cual sea el historial. El audit log de la sección 4 es el event stream; dashboards por fase con rollup semanal.

**10x menor:** CSV semanal (issue, outcome, costo) y las reglas aplicadas a ojo.
**10x mayor:** judge automático de calidad de plan y descripción, taxonomía de fallos alimentada al loop de mejora de prompts y skills, detección temprana de degradación por modelo/versión.

# 7. Trade-off final

**Sacrifico velocidad.** En orden defensivo:

- **Seguridad no se sacrifica:** el daño es irreversible y externo (credenciales, publishes públicos, CI con acceso a secrets). Un solo incidente mata el programa entero, y no solo técnicamente: mata la confianza del humano, que es el único recurso no recargable del sistema.
- **Calidad no se sacrifica:** un agente rápido pero incorrecto tiene valor neto negativo. El humano termina revisando, releyendo y arreglando más de lo que le llevaría escribir el fix. La promesa completa del sistema es "tiempo humano liberado con calidad por encima del umbral", y las métricas de la sección 6 existen justamente para verificar esa promesa.
- **Costo tiene piso y es escalable:** se acota con presupuestos duros, los sobrecostos son visibles antes de que duelan, y nunca es catastrófico.
- **La velocidad interna es lo que menos duele.** El backlog de mantenimiento es asíncrono por naturaleza: un PR que llega en 90 minutos en vez de 15 sigue siendo valioso, el humano lo revisa cuando puede, y la cola absorbe la latencia. El valor de la autonomía no está en la velocidad del loop sino en no bloquearse esperando al humano. Y ceder velocidad compra exactamente lo que sostiene todo lo demás: verificación serial completa en cada task (suite entera, no solo afectados, doble revisión en lo riesgoso, API-diff y smoke público siempre).

**Impacto concreto en el sistema real:** SLA por severidad (críticos con fast-path pre-autorizado, resto en cola), PRs que llegan más lento pero más limpios, costo por issue sube ~1.5-2x por verificación extra. El cuello de botella real no se mueve: sigue siendo la revisión humana, y esa absorbe mejor PRs limpios que PRs rápidos con dudas.

**Contra-caso honesto:** en un pipeline de hotfix de producción, la velocidad sube al segundo lugar detrás de seguridad y el sacrificado sería el costo (verificación más barata pero más rápida, con revisión humana inmediata compensando). Para mantenimiento de monorepo publicado, velocidad es el sacrificio correcto.

---

Resumen en una frase: single-agent escritor con verificación serial cara y barata en el orden correcto, límites forzados por infra, estado durable con claim exclusivo, y confianza que se concede por paquete y se retira por escape rate.
