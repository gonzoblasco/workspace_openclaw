## ¿Alguna está de más?

Analicemos las candidatas a solapamiento:

### 🔴 Posible redundancia: `workflow-pre-deploy-qa` vs `workflow-review-quality`

Ambas validan calidad. La diferencia es **cuándo**:
- **Review Quality** → pre-merge, revisión de PRs, testing, auditoría
- **Pre-Deploy QA** → post-merge, pre-producción: build, rutas, SEO, API, performance, seguridad

Son complementarias, no redundantes. Una revisa el código antes de mergear, la otra valida que todo funcione antes de deployar. **Está bien.**

### 🟡 `workflow-observability` vs `workflow-performance-optimization`

Observability **detecta** problemas de performance. Performance Optimization **los resuelve**. Son el detect/act del mismo dominio. **Está bien, es la relación correcta.**

### 🟡 `workflow-debug-investigation` vs `workflow-incident-response`

Incident Response es **en producción, con el servicio caído**. Debug Investigation es **en desarrollo, sin presión de tiempo**. Incident Response restaura el servicio primero, Debug Investigation encuentra la causa raíz después. **Está bien, son contextos distintos.**

### 🟢 `workflow-knowledge-management` vs `workflow-tech-docs`

Knowledge Management **gestiona** la documentación (consistencia, frescura, duplicación). Tech Docs **genera** documentación (ADRs, README, CHANGELOG). Una es meta, la otra es ejecución. **Está bien.**

### 🟢 `workflow-engineering-governance` vs `workflow-knowledge-management`

Governance audita **el sistema de workflows completo** (incluyendo Knowledge Management). Knowledge Management audita **solo la documentación**. Governance es un nivel de abstracción arriba. **Está bien.**
