# ADR-024: Sistema de Auto-Respuesta Inteligente con RAG + Auto-Learn + Billing

**Estado:** Aprobado  
**Contexto:** SoporteML v2 — SaaS multi-tenant para vendedores Mercado Libre  
**Stack base:** React 19 + Vite + Tailwind v4 + shadcn/ui + Supabase (PostgreSQL + RLS + pgvector)  
**Fecha:** 2026-07-20  

---

## Contexto

SoporteML recibe preguntas de compradores de Mercado Libre a través de webhooks. Cada tenant (vendedor) puede tener múltiples cuentas MeLi vinculadas vía OAuth2. Necesitamos:

1. **Clasificar** preguntas entrantes como rutinarias (auto-respuesta IA) o complejas (derivar a humano)
2. **Responder** con un pipeline RAG que busque en KB vectorial, re-rankee, y genere respuesta con contexto
3. **Auto-aprender** de preguntas históricas al conectar una cuenta MeLi
4. **Rate-limit** la API de MeLi (300 req/min) con cola y retry
5. **Facturar** por suscripción con planes según volumen de auto-respuestas

---

### b) Re-ranker sin servicio externo pago

**Decisión:** Re-ranker basado en **Cross-Encoder local con ONNX Runtime** en Edge Function, con fallback a **BM25 + cosine hybrid score**.

```typescript
// supabase/functions/_shared/reranker.ts

// Opción 1: Cross-Encoder local (ONNX)
// Modelo: BAAI/bge-reranker-v2-m3 (MIT license, ~560MB cuantizado)
// Se deploya como modelo en Supabase + ONNX Runtime

import { InferenceSession, Tensor } from 'onnxruntime-node';

let session: InferenceSession | null = null;

async function getRerankerSession(): Promise<InferenceSession> {
  if (!session) {
    session = await InferenceSession.create(
      // Modelo cuantizado int8, ~140MB
      new URL('../models/bge-reranker-v2-m3-int8.onnx', import.meta.url).pathname
    );
  }
  return session;
}

interface RerankInput {
  query: string;
  documents: Array<{ id: string; text: string; score: number }>;
}

interface RerankResult {
  id: string;
  score: number; // 0-1 normalizado
  original_score: number;
}

export async function rerank(input: RerankInput): Promise<RerankResult[]> {
  const session = await getRerankerSession();
  
  // Batch inference: pares (query, doc)
  const pairs = input.documents.map(d => [input.query, d.text]);
  const inputIds = tokenize(pairs); // tokenizer compatible con el modelo
  
  const feeds = {
    input_ids: new Tensor('int64', inputIds.flat(), [pairs.length, inputIds[0].length]),
    attention_mask: new Tensor('int64', 
      inputIds.map(row => row.map(() => 1)).flat(),
      [pairs.length, inputIds[0].length]
    ),
  };
  
  const results = await session.run(feeds);
  const scores = results.scores.data as Float32Array;
  
  // Normalizar scores con sigmoid y combinar con score original
  return input.documents.map((doc, i) => ({
    id: doc.id,
    score: sigmoid(scores[i]) * 0.7 + doc.score * 0.3, // weighted blend
    original_score: doc.score,
  })).sort((a, b) => b.score - a.score);
}

// Opción 2: Fallback sin modelo (BM25 + cosine hybrid)
export function hybridScore(
  bm25Score: number,
  cosineScore: number,
  alpha: number = 0.5
): number {
  return alpha * bm25Score + (1 - alpha) * cosineScore;
}

// En la Edge Function:
export async function rerankWithFallback(
  query: string,
  chunks: Array<{ id: string; text: string; embedding: number[] }>
): Promise<RerankResult[]> {
  try {
    // Intentar cross-encoder
    const vectorResults = chunks.map(c => ({
      id: c.id,
      text: c.text,
      score: cosineSimilarity(queryEmbedding, c.embedding),
    }));
    return await rerank({ query, documents: vectorResults });
  } catch (err) {
    console.warn('Cross-encoder falló, usando BM25+cosine:', err.message);
    
    // Fallback: BM25 + cosine similarity
    const bm25 = new BM25();
    bm25.addDocuments(chunks.map(c => ({ id: c.id, text: c.text })));
    
    return chunks.map(c => ({
      id: c.id,
      score: hybridScore(
        bm25.score(query, c.id),
        cosineSimilarity(queryEmbedding, c.embedding),
        0.4 // más peso a semántica que a keywords
      ),
      original_score: cosineSimilarity(queryEmbedding, c.embedding),
    })).sort((a, b) => b.score - a.score);
  }
}
```

**Alternativas descartadas:**
- **Cohere Rerank API:** Servicio pago, introduce latencia de red y dependencia externa. Descartado por costo y control.
- **Cross-Encoder vía API propia (GPU):** Requiere infraestructura adicional. Para MVP, ONNX en CPU es suficiente (batch de 3-5 docs es rápido).
- **Solo cosine similarity:** Pierde precisión en queries complejas. El re-ranker mejora significativamente el ranking.

**Costo del re-ranker local:**
- Modelo cuantizado int8: ~140MB en disco
- Inferencia de 3 pares: ~50-100ms en CPU (Edge Function de Supabase)
- Sin costo recurrente de API externa

### c) Estrategia de caché para MeLi API

**Decisión:** Caché de 3 capas con TTLs diferenciados por tipo de dato.

```typescript
// supabase/functions/_shared/meli-cache.ts

interface CacheConfig {
  ttl: number;        // segundos
  staleTtl: number;  // segundos que se sirve stale mientras se refresca
  invalidateOn: string[]; // eventos que invalidan esta cache
}

const CACHE_CONFIGS: Record<string, CacheConfig> = {
  // Datos de producto: cambian poco, cache largo
  'product': { ttl: 3600, staleTtl: 7200, invalidateOn: ['product_updated'] },
  // Preguntas: frescas, cache corto
  'question': { ttl: 120, staleTtl: 300, invalidateOn: ['question_answered'] },
  // Categorías: casi estáticas
  'category': { ttl: 86400, staleTtl: 172800, invalidateOn: [] },
  // Token de acceso: se cachea hasta expirar
  'token': { ttl: 21600, staleTtl: 0, invalidateOn: ['token_refreshed'] },
  // Usuario/vendedor: cambios poco frecuentes
  'seller': { ttl: 7200, staleTtl: 14400, invalidateOn: ['seller_updated'] },
};

// Capa 1: Memoria (en la Edge Function, para requests intra-función)
// Capa 2: Supabase Table (cache persistente entre funciones)
// Capa 3: Stale-while-revalidate

export async function getCachedOrFetch<T>(
  tenantId: string,
  cacheKey: string,
  type: keyof typeof CACHE_CONFIGS,
  fetcher: () => Promise<T>
): Promise<T> {
  const config = CACHE_CONFIGS[type];
  
  // 1. Intentar cache en DB
  const { data: cached } = await supabase
    .from('meli_cache')
    .select('value, expires_at, stale_until')
    .eq('tenant_id', tenantId)
    .eq('cache_key', cacheKey)
    .single();
  
  if (cached && new Date(cached.expires_at) > new Date()) {
    // Cache fresh
    return cached.value as T;
  }
  
  if (cached && new Date(cached.stale_until) > new Date()) {
    // Cache stale: servir y refrescar en background
    refreshInBackground(tenantId, cacheKey, type, fetcher);
    return cached.value as T;
  }
  
  // 2. Fetch real con rate limiting
  const fresh = await rateLimitedFetch(fetcher);
  
  // 3. Guardar en cache
  await supabase.from('meli_cache').upsert({
    tenant_id: tenantId,
    cache_key: cacheKey,
    value: fresh,
    expires_at: new Date(Date.now() + config.ttl * 1000).toISOString(),
    stale_until: new Date(Date.now() + config.staleTtl * 1000).toISOString(),
    type,
  }, { onConflict: 'tenant_id, cache_key' });
  
  return fresh;
}

// Tabla de cache
```

### d) Consistencia eventual entre webhook de MeLi y estado local

**Decisión:** Patrón **Outbox + Idempotency Key + Reconciliation Job**.

```typescript
// supabase/functions/meli-webhook/index.ts

interface MeLiWebhookPayload {
  resource: string;  // 'questions', 'orders', 'products'
  topic: string;     // 'created', 'updated'
  user_id: number;
  application_id: number;
  _id: string;       // idempotency key de MeLi
}

export async function handler(req: Request) {
  const payload: MeLiWebhookPayload = await req.json();
  
  // 1. Idempotency check (evitar duplicados)
  const { data: existing } = await supabase
    .from('webhook_events')
    .select('id')
    .eq('meli_event_id', payload._id)
    .maybeSingle();
  
  if (existing) {
    return new Response('OK (duplicate)', { status: 200 });
  }
  
  // 2. Registrar evento en outbox
  const { data: event } = await supabase
    .from('webhook_events')
    .insert({
      meli_event_id: payload._id,
      tenant_id: resolveTenant(payload.application_id),
      meli_account_id: resolveAccount(payload.user_id),
      resource: payload.resource,
      topic: payload.topic,
      raw_payload: payload,
      status: 'pending',
    })
    .select()
    .single();
  
  // 3. Responder OK inmediatamente (no procesamos acá)
  return new Response('OK', { status: 200 });
}

export async function handler() {
  const { data: pending } = await supabase
    .from('webhook_events')
    .select('*')
    .eq('status', 'pending')
    .order('created_at', { ascending: true })
    .limit(50);
  
  for (const event of pending) {
    try {
      await processEvent(event);
      await supabase.from('webhook_events')
        .update({ status: 'processed', processed_at: new Date().toISOString() })
        .eq('id', event.id);
    } catch (err) {
      await supabase.from('webhook_events')
        .update({ 
          status: 'failed', 
          error: err.message,
          retry_count: event.retry_count + 1,
        })
        .eq('id', event.id);
    }
  }
}

// Busca preguntas que MeLi dice tener pero nosotros no
export async function reconcileQuestions(tenantId: string, meliAccountId: string) {
  // Fetch preguntas de los últimos 7 días desde MeLi
  const meliQuestions = await fetchAllQuestionsFromMeLi(meliAccountId, 7);
  
  // Comparar con nuestras preguntas
  const ourIds = await supabase
    .from('meli_questions')
    .select('meli_question_id')
    .eq('tenant_id', tenantId)
    .eq('meli_account_id', meliAccountId)
    .gte('created_at', daysAgo(7));
  
  const ourIdSet = new Set(ourIds.map(r => r.meli_question_id));
  
  // Las que faltan: las insertamos
  const missing = meliQuestions.filter(q => !ourIdSet.has(q.id));
  if (missing.length > 0) {
    await supabase.from('meli_questions').insert(
      missing.map(q => ({
        tenant_id: tenantId,
        meli_account_id: meliAccountId,
        meli_question_id: q.id,
        // ... mapear campos
      }))
    );
  }
}
```

## Consecuencias

**Positivas:**
- Sistema completamente multi-tenant con RLS, sin riesgo de fuga de datos entre tenants
- Re-ranker local sin costo recurrente de API externa
- Caché de 3 capas reduce ~70-80% de llamadas a MeLi
- Consistencia eventual con outbox + reconciliation cubre todos los edge cases de MeLi
- Feedback loop permite mejorar el clasificador con datos reales
- Billing prorrateado sin lógica compleja (MP maneja los ciclos)

**Negativas:**
- El modelo ONNX del re-ranker ocupa ~140MB en la Edge Function (límite de Supabase Free: 1GB total)
- La cola de mensajes en DB no escala tan bien como Redis/RabbitMQ para >100k requests/día
- El reconciliation job cada 6h puede dejar un gap de hasta 6h si MeLi pierde webhooks
- El clasificador necesita datos históricos para ser preciso (cold start problem)

**Riesgos y mitigaciones:**
- **Cold start del clasificador:** Usar reglas heurísticas iniciales (longitud de pregunta, presencia de adjuntos, hora del día) mientras se acumulan datos de feedback
- **Overfitting del re-ranker:** Monitorear distribución de scores semanalmente; si todos los scores son >0.9 o <0.3, ajustar
- **Rate limiting de MeLi:** La cola con retry exponencial + priorización (high para webhooks, normal para sync, low para reconciliation) asegura que los webhooks nunca se pierdan por rate limit
- **Billing:** Si MP webhook falla, el cron de reconciliation de billing (cada hora) verifica el estado real de la suscripción

## Alternativas descartadas

| Alternativa | Razón de descarte |
|---|---|
| **Redis para cola de mensajes** | Overhead operativo para MVP. La cola en DB con índices funciona bien hasta ~100k requests/día. Migrar a PgMQ o Redis cuando sea necesario. |
| **Cohere Rerank API** | Costo recurrente + latencia de red. El cross-encoder local es suficientemente preciso para 3-5 documentos. |
| **Clasificador con LLM (GPT-4, etc.)** | Costo prohibitivo para clasificar cada pregunta entrante (~$0.01/request = $300/mes para 1000 preguntas/día). Un clasificador más pequeño (DistilBERT, etc.) es suficiente. |
| **Webhook síncrono (procesar en el handler)** | MeLi espera respuesta en <5s. Si el procesamiento falla, se pierde el evento. El outbox asegura durabilidad. |
| **Cache en Redis externo** | Dependencia adicional. La cache en Supabase (PostgreSQL) es suficiente para MVP y evita otro servicio. |
| **Plan gratuito con anuncios** | No alinea con el modelo de negocio. Mejor trial limitado (30 días, 100 auto-respuestas). |
