# Arquitectura de Agente Autónomo para Mantenimiento de Monorepo TypeScript

## 0. Decisión de alto nivel

**Multi-agente con orquestador + workers especializados**, con un **planificador determinista** (no LLM) para la selección de archivos. Esta es la decisión que condiciona todo lo demás, así que la justifico primero y después la desarrollo.

---

## 1. Modelo de ejecución

### Decisión: Multi-agente (orquestador + workers), con un solo LLM "caro" por tarea

**Topología:**

```
GitHub Issue
    │
    ▼
[Orquestador]  ← LLM, contexto mínimo, decide el plan
    │
    ├── [Worker: Análisis]     ← LLM, lee archivos bajo demanda
    ├── [Worker: Implementación] ← LLM, escribe código
    ├── [Worker: Verificación]  ← DETERMINISTA (no LLM)
    └── [Worker: PR]           ← DETERMINISTA (templates)
```

### Trade-offs concretos

| Dimensión | Single-agent (tool loop) | Multi-agente (elegido) |
|---|---|---|
| **Latencia** | Menor (1 round-trip de contexto) | Mayor (handoffs entre workers) |
| **Costo de tokens** | **Mucho mayor** - cada tool call re-envía el contexto acumulado | Menor - cada worker recibe solo su slice |
| **Drift de contexto** | **Alto** - el contexto crece sin límite, se contamina | Bajo - cada worker arranca limpio con un brief |
| **Coordinación** | Ninguna (simple) | Compleja - requiere protocolo de handoff |
| **Fallo de un agente** | Falla todo, hay que re-ejecutar desde cero | El orquestador puede re-lanzar solo el worker que falló |
| **Resultado incorrecto** | Difícil de aislar dónde se corrompió | Se puede auditar por etapa |

**Justificación de la elección:** en un monorepo de 200k+ líneas, el problema dominante es el **drift de contexto**. Un single-agent que acumula 50 tool calls de lectura de archivos va a terminar con un contexto de 100k+ tokens donde el modelo pierde el hilo. El costo de tokens de re-enviar ese contexto en cada llamada es el killer. El multi-agente paga el costo de coordinación (que es determinista y barato) para ganar en aislamiento de contexto y en recuperación granular.

**Qué pasa cuando un agente falla:**
- **Worker de análisis muere** → el orquestador re-lanza solo ese worker con el mismo brief. No se repite nada.
- **Worker de implementación produce código incorrecto** → la verificación determinista lo atrapa ANTES de que llegue al PR. El orquestador re-lanza con el error de verificación como feedback.
- **El orquestador muere** → es el único punto de falla. Se mitiga con persistencia de estado (sección 5): el plan ya está guardado, se retoma desde donde quedó.

**Qué haría distinto con presupuesto 10x menor:** volvería a single-agent con tool loop, pero con un **contexto estrictamente limitado** (máx 20k tokens) y un planificador determinista que pre-selecciona archivos. Sacrificaría aislamiento por simplicidad y costo.

**Con presupuesto 10x mayor:** agregaría un **worker de revisión de pares** (un segundo LLM que revisa el diff del worker de implementación antes de verificar). Esto atrapa bugs lógicos que los tests no ven. Hoy ese costo no se justifica.

## 2. Gestión de contexto

### Decisión: Índice estático + lectura bajo demanda + planificador determinista

**El problema:** 200k líneas no caben en contexto. La clave es que **el agente no necesita entender el monorepo, necesita encontrar los archivos relevantes a un issue**.

### Qué se indexa (una vez, fuera de línea)

1. **Mapa de paquetes** (`packages/*/package.json`): nombre, exports públicos, dependencias, scripts. Esto es un JSON pequeño y estable.
2. **Índice de símbolos** (via `tsc --declaration` o un indexer como `ast-grep`): para cada símbolo exportado, en qué archivo vive. Esto permite resolver "el issue menciona `Button`" → "está en `packages/ui/src/Button.tsx`".
3. **Mapa de contratos públicos**: los exports de cada paquete, que son el "API surface" que no se debe romper (crítico para la sección 3).
4. **Historial de issues resueltos**: mapeo issue → archivos tocados, para que issues similares encuentren rápido los archivos relevantes.

### Qué se lee bajo demanda

- **Solo los archivos que el planificador determinista selecciona** como relevantes al issue.
- El worker de implementación recibe: el issue, el plan, y los archivos relevantes (contenido completo, no snippets, para que no alucine sobre el contexto).

### Cómo se decide qué archivos son relevantes

**Planificador determinista (no LLM):**
1. Extraer tokens del issue (nombres de símbolos, nombres de paquetes, términos).
2. Matchear contra el índice de símbolos → archivos candidatos.
3. Matchear contra el historial de issues similares → archivos tocados antes.
4. Resolver dependencias: si el issue toca `Button`, incluir los archivos que importan `Button` (via el grafo de imports del índice).
5. **El LLM del orquestador refina** este candidato inicial, pero la base es determinista. Esto evita que el LLM "decida" arbitrariamente qué leer.

### Cómo se evita la contaminación del contexto

- **Contexto efímero por worker:** cada worker arranca con un brief limpio. No hereda el contexto de los otros.
- **TTL en el índice:** el índice se regenera en cada push a `main`. Si un archivo cambió después de que el worker lo leyó, la verificación lo detecta (el diff no aplica limpio) y se re-lee.
- **No se cachea contenido de archivos entre issues.** Cada issue arranca fresco. El único cache persistente es el índice de símbolos (que es estructural, no de contenido).

**Qué haría distinto con 10x menos tokens:** indexaría solo el mapa de paquetes y el API surface (sin índice de símbolos completo). El planificador usaría matching por nombre de paquete + grep simple. Menos precisión, mucho menos costo de indexación.

**Con 10x más:** indexaría también los tests (para que el worker de implementación vea los tests existentes del archivo que toca) y el historial de diffs (para que el worker entienda patrones de cambio previos en ese archivo).

## 3. Verificación y confianza

### Decisión: Pipeline de verificación en capas, con una "puerta de seguridad" determinista

```
Worker de implementación
    │
    ▼
[1. Typecheck]  tsc --noEmit  →  errores de tipos
    │
    ▼
[2. Lint]       biome/eslint  →  estilo + reglas
    │
    ▼
[3. Tests]      vitest run     →  tests del paquete tocado + dependientes
    │
    ▼
[4. Build]      tsc build / tsup  →  compila el paquete
    │
    ▼
[5. Contrato público]  ← DETERMINISTA, la puerta clave
    │
    ▼
[6. Diff review]  LLM de bajo costo revisa el diff contra el issue
    │
    ▼
[7. PR]
```

### La puerta de seguridad: verificación de contrato público

Este es el punto que más cuidado requiere. El agente puede "alucinar" una API que no existe, o romper un export público.

**Cómo se detecta:**
- **Antes del cambio:** snapshot del API surface de cada paquete (los exports públicos, generado por `tsc --declaration` + un script que extrae los nombres exportados).
- **Después del cambio:** regenerar el snapshot y **diffearlo contra el anterior**.
- **Regla:** si un export público cambió de firma o desapareció, el PR se marca como **"breaking change"** y requiere aprobación humana explícita, sin importar que los tests pasen. Los tests del paquete no atrapan esto porque los consumidores externos no están en el monorepo.

**Falsos positivos:**
- Un cambio que agrega un export nuevo NO es breaking (solo se marca como "nuevo API").
- Un cambio de firma que es aditivo (agrega un parámetro opcional) se marca como "potencialmente breaking" y se revisa manualmente.
- **Regla de oro:** ante la duda, marcar como breaking y pedir revisión. El costo de un falso positivo es una revisión humana de 2 minutos; el costo de un falso negativo es romper el build de un consumidor externo.
