## Análisis arquitectónico

### 1. COBERTURA

**Arquitectura (alto):** El punto de partida correcto es reconocer que no hay una "migración" sino una *reescritura incremental con coexistencia*. Next.js 16 permite convivir Server Components y Client Components en la misma app, lo que habilita la estrategia de migrar por capas/slices de ruta en vez de big-bang.

**Migración (alto):** Estrategia en 3 fases: (1) envolver la SPA existente en Next.js como un client component raíz (la app sigue funcionando idéntica), (2) migrar ruta por ruta, (3) eliminar el wrapper. Esto es lo que permite el "sin downtime" - el rollout es progresivo.

**Estado (medio-alto):** El punto crítico y donde la mayoría de las soluciones fallan. El estado global en Context API no muere - migra. La clave es mapear *qué* estado es server-side (datos) y *qué* es client-side (UI efímera, formularios, interacciones). Context API se queda para UI state; los datos viajan como Server Components.

**Rendimiento (alto):** Streaming + Suspense boundaries. Acá hay un matiz que casi nadie menciona: **el streaming no es gratis en todos lados**. Con 500 concurrentes y 2000 usuarios activos, el backend actual tiene que soportar los fragmentos de respuesta. El cuello de botella se mueve de "render del browser" a "TTFB del backend" - hay que medirlo.

**UX (alto):** Los Suspense fallbacks evitan el "flash of loading". Pero atención: 50 componentes SPA con estado global compartido significa que hay que mapear las dependencias de datos por ruta ANTES de dividir en Suspense boundaries, o el streaming genera layouts que saltan (layout shift).

**Testing (medio):** Cubre la coexistencia, pero el testing de streaming es un tema aparte: hay que testear los fallbacks de Suspense como estados legítimos, no como errores. Playwright puede testear streaming pero requiere config extra.

**Rollout (alto):** Feature flags + el wrapper de coexistencia hacen un rollout por ruta con rollback instantáneo por flag. Esto no es teoría - es la práctica estándar.

**Faltante:** No menciona observabilidad específica del streaming (métricas por fragmento), ni el impacto en el bundle de lo que queda en client (el client bundle no desaparece solo porque hay server components - hay que auditar qué cae del lado cliente).

### 2. PROFUNDIDAD

La profundidad es desigual pero con zonas muy buenas:

- **Fuerte:** La diferenciación estado server vs client. El mapeo de dependencias de datos por ruta antes de Suspense. El reconocimiento de que el cuello de botella se mueve al backend con 500 concurrentes.
- **Media:** Migración por fases (correcta pero esquemática - no detalla cómo se resuelven los edge cases de Context API que dependen de datos: `useEffect` que dispara fetch, contextos que escriben en montaje).
- **Débil:** El tema del client bundle no se toca. Tampoco la hidratación de componentes interactivos dentro de Server Components (el "client boundary" - qué pasa con los 50 componentes que usan eventos).

El detalle de la hidratación es el hueco más grande: migrar 50 componentes con estado global no es "server components y listo" - los componentes interactivos quedan como client components, y hay que decidir el árbol de boundaries con criterio, no por defecto.

### 3. ACCIONABILIDAD

Es accionable en el 80%. La fase de envolver la SPA existente y migrar por ruta con flags es implementable hoy. La distinción de estado es accionable (es un ejercicio de catálogo de contextos).

Eso requiere un patrón concreto que el análisis no llega a dar.

### 4. ORIGINALIDAD

Aporta 2 ideas que no son el cliché:

1. **"El streaming mueve el cuello de botella al backend"** - este es el insight real. Todos dicen "streaming mejora el rendimiento", casi nadie dice que con 500 concurrentes el server tiene que renderizar fragmentos bajo demanda y eso tiene costos de I/O. Original y valioso.
2. **El wrapper de coexistencia como estrategia de rollout** - no es revolucionario (es incremental adoption) pero está bien aplicado al caso de "sin downtime".

El resto es estándar competente (incremental adoption, Suspense boundaries, server vs client state) - correcto, pero no rompe moldes.
