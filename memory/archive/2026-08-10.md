## Lección de arquitectura - Modelo de agentes de OpenClaw OS (21:36)

- **Contexto:** Gonzo preguntó si podía tener conversaciones separadas en OpenClaw OS que no compartan todo (apps/artifacts), pensando que era un tema de configuración.
- **Investigación:** OpenClaw OS (thesysdev/openclaw-os) es un plugin UI que corre sobre el gateway de OpenClaw. Su AGENTS.md define el modelo: **agente = session key = thread = una conversación. No existe "nuevo chat" con un agente - siempre continuás la misma sesión.**
- **Hallazgo clave:** los "Agentes" de OpenClaw OS son los agentes del gateway (`~/.openclaw/openclaw.json`, bloque `agents.list[]`). Gonzo solo tiene `main`. El plugin `openclaw-os-plugin` expone config vacía (`configSchema.properties: {}`), asi que no hay opciones de aislamiento por config del plugin.
- **El trade-off que descartamos:** "un agente por proyecto" implica un **workspace nuevo por agente** = copias de las 115 skills, AGENTS.md/SOUL/USER/MEMORY.md, auth, y cada agente NO ve los apps/artifacts de los otros. Para el sistema de Gonzo (IA-as-infraestructura, workspace unico sincronizado por git entre 2 maquinas, memoria persistente), **duplicar todo por proyecto es un anti-patron** - no tiene sentido.
- **Conclusion (decision):** NO configurar agentes multiples. El modelo actual (1 agente `main` + sesiones con `/new`) ya da lo que Gonzo necesita: conversaciones limpias que comparten el ecosistema (skills, memoria, apps, artifacts) con historial independiente. Los agentes multiples solo valen para aislamiento duro (ej. un cliente con workspace que no debe cruzar con el personal), aceptando la duplicacion de skills como costo.
- **Regla para el futuro:** la unidad de aislamiento en OpenClaw es el AGENTE (workspace completo), no la sesion. Las sesiones dentro de un agente siempre comparten todo. No buscar separacion por conversacion - no existe el nivel intermedio.
