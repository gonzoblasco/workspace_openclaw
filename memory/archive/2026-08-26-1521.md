### 1. El problema real del estado no es clasificarlo: es la topología entre rutas

En la SPA, navegar de `/list` a `/detail` mantiene el Context montado: scroll infinito, filtros nunca serializados, estado optimista - todo sobrevive. En App Router, navegar re-renderiza server components y **todo eso se pierde salvo que viva en la URL**. "Mové los filtros a search params" no es un refactor, es una decisión de producto: qué estado merece ser bookmarkable y cuál se acepta perder. Y el patrón clásico de SPA - filter panel + results list orquestados por un provider padre con "query state" compartido - **no se puede convertir en dos islas client independientes**. Obliga a rediseñar los límites de `"use client"` página por página, algo que ningún output modeló.

### 2. Los tres caches de Next y el bug #1 de migración RSC

Hay tres capas con semánticas distintas: `cache()` de React (memo por request), Data Cache (persistente, **compartido entre usuarios**) y Router Cache (cliente). Si uno de los 10 endpoints devuelve datos por usuario y lo fetcheás con el cache default, **filtrás datos del usuario A al usuario B**. Es el error clásico de migración a RSC y ningún output lo mencionó. Auditoría obligatoria: de los 10 endpoints, cuáles son per-user (`no-store`) vs compartidos. Y post-mutación: `revalidateTag` limpia el server, pero si una isla client hizo su propio fetch, queda desincronizada. Mezclar estilos de fetching = bugs de UI stale irreproducibles.

### 3. Auth: migrar de localStorage a cookie cambia la postura de seguridad

Los server components no leen localStorage, entonces el token debe ir a cookie httpOnly. Pero un token en header `Authorization` es **inmune a CSRF**; una cookie no. La migración obliga a agregar protección CSRF a todas las mutaciones. Es un cambio en la superficie de ataque, no un detalle de plomería - y pasó invisible en los 5 outputs.

### 4. Streaming: fácil de demo, fácil de romper

Suspense en todo = "popcorn loading", peor UX que la SPA original. Además, cada stream es **una conexión abierta reteniendo un worker**: con 500 concurrentes, un endpoint lento agota el pool. Timeouts y error boundary *por boundary* son obligatorios, no opcionales. La respuesta correcta a "¿aguanta 500?" es: en capacidad, sobrado en cualquier setup; el riesgo es de corrección y de límites de duración/tamaño de respuesta streameada si vas a serverless.

### 5. ¿Los 10 endpoints deberían sobrevivir?

Todos los planes los conservan religiosamente. Pero si el backend es propio y el REST no es contrato público (¿hay app mobile o terceros consumiéndolo?), 10 endpoints se colapsan en acceso directo a datos desde los server components. Conservar la API "por las dudas" es preservar deuda.

### 6. Convivencia: lo operativo que nadie planifica

- **Design system duplicado:** un bug en un componente compartido = fix dos veces durante meses. Extraer package compartido *antes* de empezar.
- **Analytics y session replay** deben funcionar continuos en ambos mundos o perdés el baseline para probar "no empeoramos".
- **CDN:** la SPA quiere HTML no-store + assets de cache largo; RSC quiere headers por ruta. Fusionar ambas configs en el mismo dominio es trabajo real que ningún plan presupuestó.

### 7. Lo que nadie testea

- Race condition: el usuario dispara una Server Action mientras un stream viejo sigue llegando.
- **INP puede empeorar** (hydration de islas) aunque LCP mejore. Hay que medir ambos contra el baseline de la SPA, no solo celebrar el LCP.
- Botón atrás: la expectativa de cache del router de Next vs. la de la SPA difieren, y los usuarios lo notan.

### 8. Orden: spike slice, no "las fáciles primero"

Migrar primero 3 páginas **representativas** (una de lectura, una con form/mutación, una muy interactiva) de punta a punta. Así los problemas duros - auth por cookie, orquestación de estado, invalidación de cache - se exponen en la semana 1, no cuando ya migraste el 60%.

### 9. Estimación honesta

50 componentes y 10 endpoints es un proyecto de **semanas, no meses**. Lo duro (auth, auditoría de cache de los 10 endpoints, topología del Context) son días. El porting de componentes es mecánico. El boilerplate sobreestima la mecánica y subestima la semántica.

**Costo: kimi es ~6x más lento que deepseek** (2.3-5.6 min vs 21-60s) para outputs de calidad comparable.
