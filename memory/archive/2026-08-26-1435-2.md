## Changelog (el documento)

Es el **resultado**: un archivo (`CHANGELOG.md`) que lista los cambios de cada versión, en orden cronológico, con su tipo (Added/Changed/Fixed/Removed) y a veces el autor. Es lo que lee un consumidor de la librería para saber qué cambió entre versiones.

- **Qué es:** el registro histórico legible de releases.
- **Cuándo se escribe:** se actualiza en cada release (o se genera).
- **Quién lo lee:** el usuario final del paquete.

## Changeset (el insumo)

Es el **mecanismo para generarlo**: un archivo markdown que acompaña a **cada PR** y declara qué paquete cambia, qué bump (patch/minor/major) y un resumen. Cuando se mergea, la herramienta Changesets **agrupa todos los changesets pendientes y genera el changelog + la versión automáticamente**.

- **Qué es:** la declaración de impacto de un PR individual.
- **Cuándo se escribe:** en el momento del PR, antes del merge.
- **Quién lo lee:** nadie directamente — es insumo para la herramienta.

## La relación

```
PR #1 → changeset A ─┐
PR #2 → changeset B ─┼→ [Changesets agrupa] → CHANGELOG.md + bump de versión
PR #3 → changeset C ─┘
```

**Changeset = entrada individual por PR. Changelog = salida agregada por release.**

## Por qué importa la distinción

- **Sin changesets:** el changelog se escribe a mano en cada release — fácil de olvidar, desactualizar, o que quede incompleto.
- **Con changesets:** cada PR documenta su impacto **en el momento en que se hace**, cuando el contexto está fresco. El changelog sale solo, completo, sin trabajo post-merge.

## En colaboraciones a repos de terceros

**La regla es: seguí lo que el repo ya hace.** No es "obligatorio" ni "voluntario" en abstracto — es *consistencia con el repo*.

- **Si el repo usa changesets** (astryx, React, Vite, etc.): el maintainer lo espera, y a veces lo pide explícitamente en el review (como te pasó con cixzhang). Ahí **sí hay que agregarlo** — no porque te obliguen, sino porque es parte de cómo ese repo trabaja. Omitirlo es dejar el PR incompleto.
- **Si el repo NO usa changesets** (usa changelog manual, o release-please, o nada): **no lo agregues**. Imponer una herramienta que el maintainer no usa es ruido y puede hasta rechazar el PR. Ahí el changelog lo maneja el maintainer a su manera.

**El criterio no es "me obligan o no" — es "qué hace este repo".** Un changeset en un repo que no usa changesets es tan fuera de lugar como no ponerlo en uno que sí lo usa.

## Cómo saberlo rápido

Antes de abrir un PR a un repo de terceros, mirá:
1. ¿Hay carpeta `.changeset/`? → usa changesets.
2. ¿El `package.json` tiene `changeset` en scripts/deps? → idem.
3. ¿Los PRs recientes mergeados traen archivos `.changeset/*.md`? → confirmado.
4. Si no hay nada de eso → no uses changesets, seguí lo que hagan los PRs recientes.
