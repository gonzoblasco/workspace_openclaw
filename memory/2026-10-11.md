## 📚 Análisis Realizado: Lección 4 - Skills, Tools & Plugins

### 🔑 El Problema Central
El error común es confundir las tres capas (Habilidad / Herramienta / Plugin) y forzar al modelo LLM a calcular o ejecutar lo que no puede hacer de forma determinista. Esto genera:
- Agentes costosos e impredecibles.
- Rutas de ejecución indirectas peligrosas (ej. prompts → SQL).
- Conflictos entre instrucciones contradictorias.

---

### ✅ La Solución Arquitectónica

#### 1. Habilidad (Skill) 🧠
| Qué hace | Dónde vive | Costo principal |
| --- | --- | --- |
| Define el **razonamiento** y la secuencia de pasos que sigue un agente para resolver una tarea. | Se inyecta dinámicamente en el *system prompt*. | Ventana de contexto (tokens). |

- No es código, ni configuración. Es **instrucción contextualizada**.
- Ejemplo: *"Antes de ejecutar cualquier comando shell, consulta la regla de seguridad en X y valida que la acción sea permitida"*.

#### 2. Herramienta (Tool) ⚙️
| Qué hace | Dónde vive | Costo principal |
| --- | --- | --- |
| Ejecuta una **acción determinista** contra un sistema externo (API, shell, red) y devuelve resultados estructurados (generalmente JSON). | Capa de ejecución (*runtime*). | Latencia I/O y cómputo local. |

- Es lo que el modelo **puede hacer**, pero necesita ser llamado explícitamente.
- Ejemplo: Un script que ejecuta `docker ps --format json` y devuelve un array estructurado.

#### 3. Plugin 🛠️
| Qué hace | Dónde vive | Costo principal |
| --- | --- | --- |
| Gestiona el ciclo de vida, secretos, autenticación y empaqueta múltiples herramientas/skills relacionadas. | Host de OpenClaw / Entorno del sistema. | Memoria del host y arranque. |

- Es el **ancla de seguridad**. Sin él, ni la habilidad ni la herramienta pueden conectarse a sistemas externos de forma segura o persistente.
- Ejemplo: Un plugin que maneja las credenciales de Slack para que el agente pueda comunicarse con ese servicio.

---

### 🔁 Pipeline de Inyección Dinámica (Skills)

OpenClaw transforma los archivos Markdown en instrucciones XML listas para el prompt, sin reentrenar el modelo.

#### Pasos del procesador:
1.  **Lectura y validación:** Comprueba que el archivo exista y tenga frontmatter YAML válido (`name`, `version`, `description`).
2.  **Extracción de metadatos:** Separa la cabecera YAML del cuerpo Markdown.
3.  **Envoltura segura:** Las instrucciones se encapsulan en etiquetas XML, escapando automáticamente cualquier caracter malicioso (ej. si el usuario escribe `</skill>` dentro del texto, se escapa a `\u003C/skill>` para evitar que cierre la etiqueta por error).
    ```xml
    <!-- ACTIVE SKILLS INJECTION START -->
    <skills>
      <skill name="incident-triage" version="1.0.0">
        ## Procedimiento de Triaje
        1. Consulta los últimos 50 eventos del log...
        2. Filtra errores críticos (status_code >= 500)...
      </skill>
    </skills>
    <!-- ACTIVE SKILLS INJECTION END -->
    ```
4.  **Composición final:** Se une con el prompt base para formar el payload definitivo que va al modelo.

---

### 🚦 Dos Estrategias de Inyección

| Estrategia | Descripción | Cuándo usarla |
| --- | --- | --- |
| **Estática** (al inicio) | Carga todas las habilidades en bloque al arrancar. | Para lógica transversal o reglas críticas que siempre deben aplicarse. |
| **Bajo demanda** (*Just-in-Time*) | Se carga un índice ligero y solo se lee el archivo correspondiente cuando una tarea lo requiere. | Para ahorrar tokens y evitar conflictos entre habilidades contradictorias. |

---

### 🔒 Seguridad Crítica: Escaping de Etiquetas

OpenClaw **escapa automáticamente** cualquier etiqueta de cierre maliciosa (`</skill>`) que aparezca en el cuerpo del Markdown para prevenir *prompt injection*. Sin esto, una instrucción dentro de la habilidad podría terminar prematuramente y dejar al sistema expuesto.

---

### 🧭 Jerarquía de Obediencia (Conflictos)
Si dos habilidades contradicen una misma conducta:

1.  **Identidad base del agente** (prioridad máxima).
2.  **Herramientas nativas**.
3.  **Habilidades inyectadas**.

El sistema neutraliza cualquier intento de redefinir la identidad o levantar restricciones fuera de los límites permitidos.

---

### 🛡️ Principios Intransferibles
1.  **Separación estricta:** No codifiques lógica de seguridad en prompts ni gestionés secretos en archivos Markdown visibles. Usa herramientas y plugins.
2.  **Contención de riesgos:** Las herramientas dan *capacidad*, pero el plugin (backend) define los límites seguros.
3.  **El plugin es indispensable:** Sin él, no hay persistencia ni seguridad en la conexión a sistemas externos.

## Architecture & Engineering
- **Skill vs. Script Distinction:** 
    - Skills are **declarative** and **mental**: they represent the "how to think" (reasoning) and are interpreted by the LLM. They are flexible but require interpretation.
    - Scripts are **imperative** and **procedural**: they represent the "how to do" (step-by-step execution). They are static, predictable, and testable.
    - Decision: Keep Skills for logic/strategy; keep Scripts for atomic, predictable actions.
- **Technical Architecture (Skills/Tools/Plugins):**
    - **Skills:** Context-based. Live in the prompt. Define the procedure/pathway.
    - **Tools:** Execution-based. Live in the runtime. Deterministic actions (e.g., `query_db`).
    - **Plugins:** Infrastructure-based. Live in the host. Manage connections, security, and lifecycle.
- **Security & Privacy:**
    - Secrets/API Keys must **never** reside in Skills (as they are plain text in the prompt). They must be managed by Plugins.
    - Defense-in-depth for prompt injection: Neutralize (rather than just escape) control characters to prevent breaking out of skill tags.

- **Theory:** Understanding design patterns and the "why".
- **Logic:** Breaking down problems into algorithms/pseudocode.
- **Practice:** Implementation, breaking, and refactoring.
