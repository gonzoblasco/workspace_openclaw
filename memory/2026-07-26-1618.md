### 🔍 Lo que encontré

**1. El ROADMAP y los issues están desincronizados**

El ROADMAP dice "Día 1-2: Scaffold + Supabase" como un solo bloque, pero en GitHub son dos issues separados (#1 y #2). Eso está bien — los issues son la fuente de verdad granular. Pero el ROADMAP debería reflejar la estructura de issues, no inventar su propia agrupación. Si no, en dos semanas el ROADMAP y los issues van a divergir.

**2. El ROADMAP menciona "Día 5: Despliegue en Vercel" pero el issue #6 (Vercel) está en el milestone MVP v0.1 sin orden**

El orden de los issues en GitHub no está definido — no hay prioridad ni dependencias. El project board tiene columnas (Backlog, To Do, In Progress, Review, Done) pero no un orden de ejecución. Eso está bien para un kanban, pero el ROADMAP sí debería ser la fuente de verdad del orden.

**3. El issue #1 (Scaffold) menciona "Configurar PWA" pero el issue #9 (PWA offline) también**

Hay overlap. El scaffold debería tener el manifest y service worker **básico** (solo para que la app sea instalable), y el issue #9 debería ser el **offline real** (cache strategy, install prompt, etc.). Pero no está claro en los issues cuál es el alcance de cada uno.

**4. El issue #2 (Supabase) menciona "Edge Function de prueba" pero el issue #7 (IA) es la Edge Function real**

Esto está bien conceptualmente, pero el issue #2 debería ser más explícito: "Edge Function de prueba (ping)" vs "Edge Function de IA". El issue #7 debería referenciar que depende del #2.

**5. Falta un issue de "Auth UI"**

El issue #2 menciona "Configurar auth (magic link)" pero eso es backend. No hay un issue para la UI de login (página de login, formulario de email, estado "check your email", callback). Eso es frontend y debería ser un issue separado o parte del #1.

**6. El `.env.example` tiene `OLLAMA_CLOUD_MODEL=deepseek-v4-flash`**

Pero en el BRIEF dice "DeepSeek V4 Flash / Gemma 4". Debería ser consistente. Además, ¿necesitamos `OLLAMA_CLOUD_API_KEY`? Ollama Cloud no usa API key tradicional, usa el endpoint de Ollama. Habría que verificar qué variables necesita realmente.

**7. El BRIEF menciona "shadcn/ui" pero el issue #1 menciona "ESLint + Biome"**

Biome reemplaza ESLint. Tener ambos es redundante. El stack de Gonzo usa Biome, no ESLint. El issue #1 debería decir solo Biome.

**8. El CONTRIBUTING.md dice "Merge con squash" pero el repo tiene `allow_squash_merge: true` y `allow_merge_commit: true` y `allow_rebase_merge: true`**

Si la política es squash, deberíamos deshabilitar merge commit y rebase merge en el repo. O al menos documentar que preferimos squash.

**9. Falta configurar `delete_branch_on_merge`**

El CONTRIBUTING dice "La branch se elimina después del merge" pero el repo tiene `delete_branch_on_merge: false`. Debería ser `true`.

**10. El project board no está vinculado al repo**

**11. No hay un issue para "Configurar Supabase client en el frontend"**
