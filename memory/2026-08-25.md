## Sesion: astryx #5373 - respuesta a review (08:40-08:55)

Gonzo me paso el link de un comentario de rubyycheung en el PR #5373 de astryx ("Improve Popover responsive fit and focus behavior"). ### El review de Gonzo (24/08) y como los respondio rubyycheung
Gonzo reviso el PR enfocado en la parte de focus (cambia como se anuncia un Popover tipo dialog). 4 puntos:

1. **AT pass del `tabIndex={-1}` dialog container** - el patron (focus a container `role="dialog"` con tabIndex=-1 + aria-modal sin controles) es donde mas divergen los screen readers. Pidio validar al menos NVDA+Chrome y VoiceOver+Safari en la story "Read only".
   → **Respuesta:** agrego story dedicada de Read-only dialog con los checks manuales exactos (nombre/rol anunciado, Tab fwd/reverse, Escape, focus return), y marco NVDA+Chrome y VoiceOver+Safari como follow-up explicito (no "not verified" silencioso).

2. **Guard explicito para `focusable` vacio en `useFocusTrap`** - el branch nuevo (`document.activeElement === container`) corre despues de `first`/`last`; si `focusable` esta vacio, `last` es undefined y Shift+Tab llama `last.focus()`. Gonzo planteo "worth an explicit guard" sin verificar contra codigo real (leccion del 24: no afirmar sin verificar).
   → **Rubcheung:** confirmo que el focus trap YA tiene un guard explicito `focusable.length === 0` antes de computar first/last (test existente lo cubre) + agrego cobertura de entrada inversa (Shift+Tab desde el contenedor con foco programatico).

3. **Costo de medicion (2 observers + window listeners en cada open)** - ResizeObserver + MutationObserver(subtree) + load/resize/visualViewport, y re-mide en cada children change. Riesgo de jank en contenido que se actualiza frecuente. Gonzo sugirio throttle con requestAnimationFrame (coalescing).
   → **Rubcheung:** resize, mutation, image-load, window-resize, visual-viewport y children-change ahora se coalescen a UNA medicion de overflow por animation frame + test de regresion que dispara varias senales y verifica que solo se programa un frame.

4. **Split `role="none"` vs dialog** - el container `tabIndex={-1}` solo cuando role=dialog. Si un Popover usa role=none con un menu adentro, el wrapper no es focus target programatico. Gonzo confirmo que eso es correcto (el menu tiene items focusables) - solo queria confirmar el split.
   → **Echeung:** confirmo que el split es intencional: roles content-owned (menu/listbox) tienen su propio modelo de foco y no hacen del wrapper neutro un focus target. Docs y tests cubren el contrato.

Ademas: rebaseo sobre main actual y resolvio el conflicto de Popover con el wrapper de layer-depth.
