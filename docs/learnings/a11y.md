## 2026-08-12 - Colaboración OSS: astryx #4914 + radix #4109 (sesión de a11y)

**Context:** Sesión de colaboración en accesibilidad. Refiné el PR #4914 de astryx (fix de CI con 5 findings de review) y abrí el PR #4109 de radix (aria-posinset/setsize en Select). Varias lecciones de proceso.

**Lesson - buscar issues de a11y en repos maduros: la mayoría ya tienen PRs o el maintainer no quiere cambios:**
- Barrido por radix, ariakit, adobe, mui, vercel, react.dev, TanStack. Casi todos los issues "obvios" tenían PRs abiertos (react.dev #8552 tenía 4 PRs compitiendo), maintainer que no quiere cambiar (mui #46319), o bugs sin solución clara (adobe #10310).
- El issue ideal: bug concreto + sin PR + alcance acotado + repo con apetito a11y. radix #3962 cumplía todo.
- **Siempre verificar antes de atacar:** (1) si ya hay PRs que referencian el issue, (2) si el repo realmente tiene el componente (radix #4085 sobre "Command" estaba mal dirigido - radix no tiene Command, es de cmdk).

**Lesson - el deepen-and-retry tiene dos trampas de git que no son obvias:**
- El refspec del fetch necesita el nombre de rama SIN el prefijo `origin/` (el `--base` llega como `origin/main`, y `origin ${baseBranch}:...` produce `origin origin/main:...` que falla).
- `git fetch --deepen` solo actualiza `FETCH_HEAD`, no el ref `origin/<base>`. Hay que escribir `refs/remotes/origin/<base>` explícito, o el three-dot retry (que referencia `origin/main`) sigue sin resolver.
- Verificado con repo sintético: el deepen recupera el resultado EXACTO (modifiedComponents: ["Card"]) en vez del over-reportado del fallback. Esto valida que deepen-and-retry es mejor que degradar directo.

**Lesson - el patrón de roving focus en listbox scrollable rompe el conteo de VoiceOver+Chrome:**
- Radix Select usa foco real en cada option (roving focus) dentro de un listbox scrollable, sin aria-posinset/aria-setsize. VoiceOver+Chrome cuenta solo los options visibles en el viewport → total incorrecto. Safari/NVDA funcionan por heurística.
- El fix: declarar aria-posinset/aria-setsize explícitamente, calculados desde el DOM (el contenedor de lista es el parentElement del option: el role="group" si hay grupo, si no el viewport). Maneja grupos correctamente (cada group cuenta independiente, patrón APG).

**Self-reflection:**
- CONTEXT: colaboración OSS en a11y (refinar PR + abrir PR nuevo)
- REFLECTION: el flujo fue bueno. En astryx implementé los 5 findings de la review con tests reales y verificación empírica (repo sintético). En radix hice el análisis de causa raíz riguroso (verifiqué el APG, el patrón de roving focus vs activedescendant, y que radix no tiene Command). El único pendiente es la validación con VoiceOver+Chrome que solo Gonzo puede hacer.
- LESSON: en bugs de a11y de screen readers, el análisis de causa raíz (qué patrón usa la librería, qué espera el lector) vale más que el fix a ciegas. Y verificar el estado real (PRs existentes, componente existente) antes de invertir tiempo.
- BIASES DETECTED: none (el proceso de verificación previa evitó anclarme en issues mal dirigidos).

**Tags:** Colaboración OSS: astryx #4914 + radix #4109 (sesión de a11y)

## 2026-08-20 - Reviews de bots pueden detectar regresiones reales (no solo P2 de corrección)

**Context:** PR #5551 en mui/base-ui (quitar aria-orientation inválido del rol grid). Mi primer fix eliminó `orientation` del `useListNavigation`, lo que rompía la navegación grid horizontal (flechas izq/der) porque el hook caía al default vertical. El bot Codex (automatizado) lo detectó como P1.

**La lección - contradice parcialmente la nota anterior (2026-07/08) de que los bots solo dan feedback P2:**
- Los reviews de bots SÍ pueden detectar regresiones funcionales reales, no solo correcciones cosméticas. En este caso, el bot notó que quitar una prop afectaba la navegación además del atributo.
- El fix correcto: **separar navegación de atributo ARIA**. Mantener `orientation: 'horizontal'` para la navegación, pero suprimir solo el `aria-orientation` del DOM cuando el rol no lo soporta (`delete merged['aria-orientation']`). No eliminar la prop entera.

**Regla práctica:** al tocar una prop que alimenta un hook de navegación/behavior, verificar si esa prop también genera atributos de salida. Eliminar la prop puede romper el behavior además de quitar el atributo. La solución correcta es suprimir solo el atributo de salida, no la prop de entrada.

**Self-reflection:**
- CONTEXT: fix de aria-orientation en base-ui grid
- REFLECTION: mi primer approach (quitar orientation) era demasiado amplio - rompía la navegación. El bot lo detectó y la corrección (suprimir solo el atributo) fue la correcta.
- LESSON: los reviews de bots merecen lectura técnica, no descarte ni aceptación ciega. Y al modificar props de hooks de navegación, separar behavior de atributos de salida.
- BIASES DETECTED: anchoring (me anclé en "el atributo es inválido" y eliminé la fuente completa, sin considerar que también alimentaba la navegación).

**Tags:** Reviews de bots pueden detectar regresiones reales (no solo P2 de corrección)

## 2026-08-23 - Cambiar a role="presentation" puede crear un trade-off de violaciones ARIA (astryx #5344)

**Context:** PR facebook/astryx #5344 (fix selector: render in-listbox dividers as presentation). El bug era real (divider con `role="separator"` dentro de un `listbox` = violación crítica axe `aria-required-children`). Mi fix cambiaba el divider a `role="presentation"`. El maintainer eligió el PR alternativo #5107 (aria-hidden) porque mi approach tenía un trade-off invisible.

**La lección - al cambiar un role ARIA, verificar qué atributos ARIA escribe el componente por defecto:**
- `Divider` siempre escribe `aria-orientation`. `role="presentation"` NO permite `aria-orientation`. Entonces axe cambiaba `aria-required-children` (crítica x1) por `aria-allowed-attr` (crítica x1) en el mismo elemento = **crítica x2**. Un role restrictivo puede crear un trade-off de violaciones, no resolver el problema.
- El fix superior (#5107): `aria-hidden="true"` en el Divider. Mantiene el visual y el `role="separator"` en el DOM, pero lo saca del árbol de accesibilidad por completo. Sin nuevo API surface, sin trade-off.
- Este tipo de detalle solo se ve en un axe run - no es obvio leyendo el código.

**Regla práctica:** antes de cambiar un role ARIA a uno más restrictivo (presentation, none), revisar qué atributos ARIA escribe el componente por defecto. Si escribe atributos que el role nuevo no permite, el fix puede empeorar el conteo de violaciones. `aria-hidden` suele ser más limpio para elementos puramente visuales que no aportan info.

**Self-reflection:**
- CONTEXT: fix de a11y en astryx selector
- REFLECTION: el diagnóstico del bug era correcto y el maintainer lo reconoció, pero mi approach de solución tenía un trade-off que solo un axe run revela. El cierre no fue un rechazo al trabajo - fue una decisión de diseño donde el approach alternativo resultó más limpio.
- LESSON: al proponer fixes de a11y, validar el approach con un axe run real antes de abrir el PR, no solo el diagnóstico del bug. Y considerar `aria-hidden` como alternativa a cambiar roles restrictivos.
- BIASES DETECTED: none (el maintainer explicó el trade-off con claridad; no hubo sesgo de mi parte, solo falta de validación con axe).

**Tags:** Cambiar a role="presentation" puede crear un trade-off de violaciones ARIA (astryx #5344)
