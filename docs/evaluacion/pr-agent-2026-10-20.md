Medición de la calidad real de PR-Agent con modelos servidos por Ollama, contra
PRs públicos que **ya tienen revisiones humanas** como verdad de base, y con un
juez independiente (modelo distinto al que generó cada output).

Conclusión corta: **el review automático no alcanza el nivel de la revisión
humana, y para redactar descripciones de PR es claramente inferior a Claude
Code con el mismo modelo.** PR-Agent queda útil por su integración (GitHub
App/Action que dispara solo) y sus salidas estructuradas, no por la calidad del
texto.

## 1. Qué es PR-Agent (no es lo que parece)

- **No** es una app con dashboard ni un hub. No hay frontend: la única web del
  repo es la doc de Docusaurus. Los servidores son webhooks (Starlette/FastAPI).
- Se integra a GitHub como **GitHub Action** (workflow) o **GitHub App
  self-hosted** (se crea en el Developer Portal).
- **No hay marketplace**: cero referencias en el repo, y la API de GitHub no
  lista ninguna app de PR-Agent.
- El producto de negocio de esta línea es **Qodo** (plataformeado), que donó
  PR-Agent a la comunidad OSS. Es el legacy OSS de su producto.

## 3. Review automático: no alcanza al humano

Caso `encode/httpx#3769`. La verdad de base: dos revisores humanos apuntan al
mismo bug central: dentro del bloque `finally`, el `for` sobre `self._mounts`
no tiene `try/finally` por transporte, así que si un mount lanza al cerrarse
los mounts posteriores quedan **abiertos** (fuga de recursos). Afecta a los 4
métodos: `close`, `__exit__`, `aclose`, `__aexit__`.

| Vía | Hallazgos | Juez |
|---|---|---|
| review `--pr_url` (gpt-oss) | 0 | n/a |
| review plain-diff (gpt-oss) | 1 ("Exception Masking") | **1/10** |
| ask plain-diff (gpt-oss) | 5 falsos positivos | **0/10** |
| server A2A en Docker | "No major issues detected" | **0/10** |
| `kimi-k2.6:cloud` | 0 | n/a |
| `deepseek-v4-pro:cloud` | 0 | n/a |
| `gemma4:12b-mlx` (local) | se colgó (RAM) | n/a |

Caso `pydantic/pydantic#13953`: 0 hallazgos; los 3 revisores humanos lo
encontraron.

El único hallazgo de PR-Agent ("Exception Masking") es **adyacente pero no es el
bug real**: el juez lo marcó como falso positivo.

**No es un problema de parseo**: el output crudo muestra que
"No major issues detected" es la salida real del modelo, no findings que
PR-Agent perdió al parsear.

**No es un problema de integración**: los 4 modelos fallan igual. La causa es la
calidad del modelo sobre este tipo de código, más un prompt (`pr_reviewer`) que
produce salida estructurada pero sin el acierto.

## 4. Descripciones de PR: inferior a Claude Code

Mismo modelo (`minimax-m3.1-flash:cloud` vía Ollama) y mismo diff para las dos
herramientas: el diff real del script propio de Onyx (425 lineas) del propio
workspace.

| | chars | ¿menciona los 5 hechos clave del cambio? |
|---|---|---|
| PR-Agent `describe` | 4752 | **0 de 5** |
| Claude Code | 2499 | **5 de 5** |

Los 5 hechos que PR-Agent no menciona: la ruta duplicada
(`deployment/docker_compose/deployment/docker_compose`), el filtro de containers
que no leía los cuatro campos de `docker ps`, el límite de 8 GB de Docker
Desktop, y por qué el CI fallaba por rutas absolutas.

Defectos de formato visibles en el cuerpo del PR:

- El **title sale literal `None`** (`generate_ai_title=false` por default; en
  plain-diff no hay PR del que sacarlo).
- File Walkthrough con **14 links `href=""`** (vacíos) y **14 conteos `+-1/--1`**
  (placeholder).
- Declara **"10 files"** cuando el diff tiene **14**.
- En `--pr_url` **no imprime**: solo publica, o queda en `settings.data`
  (`push_outputs` solo dispara con `publish_output=true`). Para usarlo en un
  flujo hay que habilitar publicación real.

**Causa de fondo**: PR-Agent comprime el diff a un prompt; Claude Code explora
el repo con un loop agéntico (grep, leer archivos, tests) y de ahí sale el
contenido real.

Dato de contexto: la descripción humana de `pydantic#13884` (4151 chars) usada
como verdad de base termina con *"🤖 Generated with Claude Code"*, o sea, en la
práctica **la barra de calidad de una descripción de PR la pone Claude Code**,
no una persona.

## 5. Recomendación de uso

- **Descripciones de PR** → Claude Code (ya instalado, ya ruteado por Ollama
  con `ANTHROPIC_BASE_URL=http://127.0.0.1:11434`).
- **Review de PR** → no delegar en PR-Agent. Sirve como segunda opinión para
  explorar ideas (`ask`), y `describe`/`improve` como generadores de borrador.
- **Lo que sí aporta PR-Agent**: la integración (GitHub App/Action que dispara
  solo, sin que alguien esté mirando) y las salidas estructuradas.

## 6. Trampas técnicas (verificadas)

1. **El bearer no puede ir por env var.** Dynaconf reconstruye la sección desde
   las env vars de esa sección al importar `pr_agent.mosaico.server` y pierde el
   decodeo `@json` (queda `str`); `MosaicoAuthenticationBackend` aborta el
   arranque. Va por TOML (`.secrets.toml`) → `DataDict`.
2. **Los modelos de razonamiento necesitan presupuesto de salida holgado.**
   `gpt-oss` gasta tokens en el bloque `reasoning`; con `max_tokens` chico
   devuelve `content:""` + `finish_reason:length` **sin error visible** →
   `max_output_tokens=16000`.
3. **Los timeouts del health probe se escalonan**: compose (100 s) > cliente HTTP
   (70 s) > probe del server (30 s). Con budgets iguales el container cae a
   `unhealthy` con un `503` que en realidad es timeout transitorio.
4. **`config.publish_output` NO es host-only.** Un `.pr_agent.toml` del repo
   podría poner `publish_output=true` y publicar en GitHub pese al `false` del
   host. Se cierra con `use_repo_settings_file = false`.
5. **Flags antes del comando**: `--output`/`--json-output` van antes del verbo, o
   el CLI imprime el help. `--json-output` solo existe para `review`/`review_pr`;
   `--output` solo en modo plain-diff.
6. **Un hunk con el conteo de líneas mal escrito** revienta `unidiff` y el CLI
   también imprime el help en vez de fallar claro. Generar el diff con
   `git diff`. Diagnóstico: si el CLI imprime el help, el error real está
   **arriba** en el log (capturar `head`, no `tail`).
7. **El modelo local con contexto 262k** deja la RAM al 14 % con 7.8 GB de swap y
   el cliente se cuelga esperando el lock. Ollama sí responde (55 s), el que se
   cuelga es el cliente.
8. **El clone deja los archivos en `0600`** y el usuario no-root del container no
   puede leer `/app` → `PermissionError`. Fix en el host (`chmod -R a+rX`) y
   rebuild.

## 7. Metodología (reutilizable)

1. Elegir PRs **públicos que ya tengan revisiones humans**: eso es la verdad de
   base. Un PR sin reviews no prueba nada.
2. Correr PR-Agent **con `publish_output=false`** y verificar que el PR ajeno
   quedó intacto (contadores de comentarios antes/después).
3. **Juez con modelo DISTINTO** al que generó el output.
4. Cuidado: el juez hay que darle la verdad de base **solo del PR evaluado**. Si
   se mezclan dos PRs, penaliza hallazgos que no correspondían.
5. El juez debe marcar **falsos positivos** además de detección: un issue que no
   es un bug real es un error del agente.
