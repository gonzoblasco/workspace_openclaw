### Hallazgos tecnicos medidos (Chromium 153, chrome-headless-shell, estructura real del componente)
Metodo: sondas HTML propias en `/tmp/anchor-probe/probe*.html` ejecutadas con `chrome-headless-shell --headless --dump-dom`. Reproducible.

- **`position: fixed` es necesario (C5)**: con `absolute` el containing block queda dentro del componente y `anchor()`/`anchor-size()` NO resuelven (used `top: 0px`, used `width: 145px`, caja final 153x21 = la caja de VisuallyHidden). Con `fixed` sale de la cadena y resuelve por nombre. Control que aisla: con el ancla como **hermana** (no ancestro), `absolute` SI funciona -> es la relacion de ancestro, no `absolute` en si. Ademas es inerte sin soporte (con los valores descartados el input conservo la geometria 1x1 previa).
- **RTL (C6)**: `left`/`top` fisicos con `anchor()` funcionan en RTL. `inset-inline-start: anchor(left)` **ROTO en RTL** (el input cae a -208px, un ancho entero al otro lado); `anchor(right)` queda 8px corrido. El `inset` shorthand funciona LTR y RTL. Conclusion: **si a `inset`, no a propiedades logicas** (`anchor()` toma lados fisicos).
- **Bonus**: con `width: anchor-size(width)` la caja sale **8x6 px mas grande** que el componente (`anchor-size` dimensiona content box; el input suma borde+padding del UA). El test pasa igual porque `covers()` tolera hasta 2px de sobra. El shorthand `inset` o `anchor-size` + `box-sizing: border-box` dan medida exacta.
- **Hallazgo A - el id por instancia es obligatorio**: con 4 hosts usando el MISMO `anchor-name` sin `anchor-scope`, los 4 inputs resolvieron al mismo ancla (dy 585/533/481/429) y ninguno cubrio al suyo. `anchor-scope` lo arregla, pero salio despues que el anclaje (Chrome 131 vs 125) -> hay ventana Chrome 125-130 donde duplicados colisionarian. No se puede reemplazar el id unico por un nombre estatico.
- **Hallazgo B - scroll (sin confirmar)**: con `position: fixed`, dentro de un contenedor con `overflow-y: auto` con `scrollTop = 40` los 6 componentes quedaron **40px corridos** (no siguen el scroll). Dato fuerte: el spike borrado en `cedc9e3` se llamaba "Spike v5: **scroll tracking** + clip disambiguation for fixed+anchor hidden input" -> ya era problema conocido. **Requiere confirmar en Chrome real (no headless) antes de tratarlo como bug.**
- **`anchor-scope`/`anchor-name`/`position-anchor` camelCase**: CSSOM si expone `style.anchorName` / `style.positionAnchor`; React maneja custom properties (`--x`) con `setProperty` (verificado en `react-dom-client.development.js`).
- **Custom property leida en host e input (C4)**: la var tiene que ir en AMBOS lados. Con la var solo en `position-anchor` del input, un consumidor con `anchor-name` por classname sigue enmascarado por nuestro default inline (computed quedaba en el default y el input dejaba de cubrir). Con var en host + input: funciona en 3 casos (sin override, override por classname, override sin default).
- **Precedente en el repo**: ya se exponen variables CSS como API publica (`--trigger-anchor-point` en Popover.tsx:327 y Tooltip.tsx:236, `--trigger-width`, `--table-row-level`, `--tree-item-level`).

### Correccion C2 (Math.random) - causa raiz
`React.useId` **no existe antes de React 18**; el paquete declara `react: ^16.8.0 || ^17 || ^18 || ^19.0.0-rc.1`. Eso rompio CI: en `79e3cc9de` fallaron `test-16` y `test-17`; el commit `0cf378d7b` los paso a verde cambiando a `Math.random` ("replace useId with random ID to fix CI tests crash"). `Math.random` rompe SSR (valor distinto entre server y cliente -> mismatch de hidratacion en el atributo `style`). Salida correcta: `useId` de **`react-aria/useId`** (resuelve `React.useId` en 18+, contador en 16/17) que ya usan `Button.tsx:34`, `Dialog.tsx:44`, `Disclosure.tsx:49`, `Tree.tsx:118`. Hay que mantener el sanitizador: el id de React trae `:` en 18 y dos puntos no es `<dashed-ident>` valido. (En React 19 el SSR devuelve `_R_0_`.)
